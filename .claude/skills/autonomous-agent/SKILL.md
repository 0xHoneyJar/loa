# Autonomous Agent Orchestrator

<objective>
Orchestrate the full Loa lifecycle — discovery through learning — passing every quality gate, with self-audit and bounded remediation loops.
</objective>

<prime_directive>
## Prime Directive

Pass every gate; when uncertain, STOP and ASK rather than proceed on assumptions (in unattended runs: record the assumption in NOTES.md Decision Log per CLAUDE.loa.md principle 1 and proceed).
</prime_directive>

<execution_model>
## Execution Model

PREFLIGHT → DISCOVER → DESIGN → IMPLEMENT → AUDIT → (pass? SUBMIT : REMEDIATE, loop ≤3 then ESCALATE) → POST-PR-VAL → READY_FOR_HITL → DEPLOY → LEARN. See `resources/phase-mechanics.md` when a phase's exit criteria, exact invocation commands, exit codes, or schemas are needed, and `resources/phase-checklist.md` when completion needs more detail than that.
</execution_model>

<operator_detection>
## Operator Detection

Loa adapts behavior to the operator type (see `resources/operator-detection.md` when the full adaptation matrix is needed).

```yaml
# .loa.config.yaml
operator:
  type: auto | human | ai
  ai_config:
    enforce_autonomous_skill: true
    strict_quality_gates: true
    require_audit_before_pr: true
```

When `type: auto`, checked in order, first match wins → `operator_type: ai` (otherwise `human`): a Clawdbot runtime (`CLAWDBOT_GATEWAY_TOKEN`/`CLAWDBOT_GATEWAY_PORT` env var, or `$HOME/.clawdbot/clawdbot.json`); another AI environment (`CLAUDECODE=1`, `LOA_OPERATOR=ai`, `CLAWDBOT_AGENT=true`); a Moltbot workspace signature (2+ of `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `HEARTBEAT.md`, `TOOLS.md`, `USER.md`, `WORKLEDGER.md` — skip an `AGENTS.md` whose first line contains `generated by agents-md-gen.sh`, Loa's own projection, not a marker); or a non-interactive session. AI operators load `ai_config`.

A human operator gets interactive, flexible handling; an AI operator is auto-wrapped (e.g. `/implement task-1` → `/autonomous --target implement`) with mandatory audit and strict gates when `ai_config.enforce_autonomous_skill: true`.
</operator_detection>

<phase_0_preflight>
## Phase 0: Preflight

**Purpose:** Restore context, verify integrity, detect the operator, and select work.

Archive previous-cycle artifacts with `.claude/scripts/workspace-cleanup.sh --grimoire grimoires/loa --yes --json`; a security error (exit 3) or a detected partial archive state MUST halt the workflow. Detect the operator per Operator Detection above. Read `grimoires/loa/NOTES.md`'s "Session Continuity" section and HALT on any CRITICAL blocker; load the prior trajectory when continuing work. Confirm `.loa-version.json` exists (Loa is mounted) — if not, halt and tell the user to run `/mount`. Select the highest-priority "Ready" item from `WORKLEDGER.md` (or equivalent; else the backlog or `HEARTBEAT_OK`) and log it. Zero the token counters and load the attention-budget thresholds from config.
</phase_0_preflight>

<phase_1_discovery>
## Phase 1: Discovery

**Purpose:** Understand requirements fully before designing. Triggered by new work with no existing PRD.

If the codebase hasn't been analyzed, run `/ride`, wait for the `reality/` artifacts, and verify every grounding claim carries a file:line citation. Run `/plan-and-analyze` (discovering-requirements skill) through every discovery phase to generate the PRD at `grimoires/{project}/prd.md`, and verify it covers: summary, evidenced problem statement, measurable goals, user stories with acceptance criteria, technical constraints, dependencies, and risk mitigations.

### 1.4 Flatline PRD Review

**Purpose:** Adversarial multi-model review at each planning gate — the PRD here, the SDD at §2.3, and the Sprint plan at §2.5.

When `flatline_protocol.enabled` and `autonomous_mode.enabled`: run `flatline-orchestrator.sh --doc grimoires/loa/prd.md --phase prd --autonomous --run-id "$run_id" --json`, then `flatline-result-handler.sh --mode autonomous --document grimoires/loa/prd.md --phase prd --run-id "$run_id"`. Exit 0 continues to Phase 2; exit 1 (BLOCKER) or exit 4 (disputed threshold) escalates and stops the workflow (same at §2.3/§2.5). Log `"Flatline {phase} Review: {N} integrated, {M} disputed, {K} blockers"` to NOTES.md; skip and log when disabled.
</phase_1_discovery>

<phase_2_design>
## Phase 2: Design

**Purpose:** Architecture and planning before implementation.

Run `/architect` (designing-architecture skill) to generate the SDD at `grimoires/{project}/sdd.md` — system diagrams, component design, data flow, API contracts, security considerations. Run `/sprint-plan` (planning-sprints skill) to generate `sprint.md`: atomic tasks, acceptance criteria per task, dependencies mapped. Verify the SDD traces to every PRD requirement, tasks are atomic and testable, and there are no circular dependencies.

### 2.3 Flatline SDD Review

Run the canonical Flatline gate (§1.4) with `--doc grimoires/loa/sdd.md --phase sdd`; exit 0 continues to Sprint review.

### 2.5 Flatline Sprint Review

Run the canonical Flatline gate (§1.4) with `--doc grimoires/loa/sprint.md --phase sprint`; exit 0 continues to Phase 3 (Implementation).
</phase_2_design>

<phase_3_implementation>
## Phase 3: Implementation

This phase hands off to `/run sprint-plan` (or `/run sprint-N`). Verify beads tasks exist, monitor the run, and don't proceed until it completes or halts; report a halt (circuit breaker) to the user rather than bypassing it. For each task in `sprint.md`: read its acceptance criteria, run `/implement`, apply Tool Result Clearing after searches, run the relevant tests, commit with a conventional message, log to the trajectory, and update the task's status. Continuously run linters/formatters and unit tests as changes land, watch for secrets or vulnerabilities, and respect the attention budget.

### Implementation Guard

**NEVER**: Write application code directly in this phase — all code flows through `/run` → `/implement` → `/review-sprint` → `/audit-sprint`, and `implement-gate.sh` fail-asks App-Zone writes outside that path.
</phase_3_implementation>

<phase_4_audit>
## Phase 4: Audit (MANDATORY)

**Purpose:** Verify quality before any external action.

Run `/audit-sprint` (auditing-security skill) across every dimension — security (auth, injection, secrets), architecture (patterns, coupling, cohesion), code quality (complexity, duplication, naming), DevOps (CI/CD, monitoring, docs), and domain-specific concerns — scoring each 1-5 against `RUBRICS.md` (see `resources/quality-gates.md` when the full per-dimension definitions are needed). PASS requires every dimension ≥ `audit_threshold` (default 4); the report states PASS/FAIL, per-dimension scores, findings with severity, remediation guidance, and evidence citations. All scores ≥ threshold → Phase 5 (Submit); otherwise → Phase 4.5 (Remediation).
</phase_4_audit>

<phase_4_5_remediation>
## Phase 4.5: Remediation Loop

**Purpose:** Fix audit failures until quality passes.

Parse the findings, sort by severity (CRITICAL > HIGH > MEDIUM > LOW), and identify root causes. For each CRITICAL or HIGH finding: understand the issue, design the minimal fix, apply it, verify locally, and log to the trajectory. Re-run `/audit-sprint` and increment the remediation-loop counter. All scores ≥ threshold → proceed to Phase 5; loop count > `max_remediation_loops` (default 3) → escalate to a human with an escalation report (summary, attempts made, remaining failures, recommendation) and halt; otherwise repeat.
</phase_4_5_remediation>

<phase_5_submit>
## Phase 5: Submission

**Purpose:** Create a high-quality PR. Enter only if Phase 4 audit PASSED.

Push the branch to the fork/origin and verify the push succeeded. Create the PR with a conventional-commit-format title and a body containing the summary from the PRD, the changes from `sprint.md`, a link to the audit report if applicable, and a trajectory summary. Verify the title is descriptive, the body explains context, and there are no secrets in the diff.
</phase_5_submit>

<phase_5_5_post_pr_validation>
## Phase 5.5: Post-PR Validation

**Purpose:** Validate PR quality before human review. Enter only if `post_pr_validation.enabled: true` in `.loa.config.yaml`.

Run `.claude/scripts/post-pr-orchestrator.sh --pr-url <pr_url> --mode autonomous`; success sets state to `READY_FOR_HITL`, any other exit HALTS. When disabled, skip to Phase 6 or Phase 7. State lives in `.run/post-pr-state.json`. Resuming after a context clear: see Resume Support, below.
</phase_5_5_post_pr_validation>

<phase_6_deploy>
## Phase 6: Deployment (Optional)

**Purpose:** Safely deploy and verify. Gate: Post-PR Validation passed (or state = READY_FOR_HITL) AND (`require_human_deploy_approval == false` OR approval received).

Run `/deploy-production`, monitor progress, and capture deployment logs. Run `/audit-deployment` and verify health checks pass, error rate hasn't increased, performance is within bounds, and functionality works. If the deploy audit fails: roll back, verify it, log the incident, and escalate.
</phase_6_deploy>

<phase_7_learning>
## Phase 7: Learning

**Purpose:** Improve from experience, iterate on the PRD, feed learnings upstream.

Classify PRD deviations found in the trajectory as major (invoke `/refine-prd` or escalate) or minor (log to NOTES.md); see `resources/prd-iteration.md` when the gap classification needs more detail. Capture feedback to `grimoires/loa/feedback/{date}.yaml`; see `resources/feedback-protocol.md` when writing entries (types and targets). Record significant learnings as structured notes and update NOTES.md with a session summary; see `resources/structured-notes.md` when a note needs a type and expiry. Archive the trajectory to `trajectory/{date}.jsonl`, clear working memory, mark the work item complete, and — if `/refine-prd` was invoked — wait for the new `sprint.md` before moving to the next item.
</phase_7_learning>

<resume_support>
## Resume Support

The `/autonomous --resume` flag resumes workflows halted by a Flatline BLOCKER or by a Post-PR context clear.

### Resume from a Flatline Halt

Check for a pending escalation: `escalation=$(.claude/scripts/flatline-escalation.sh list | jq '.[0]')`. If found, extract `run_id`, `phase` (`prd`/`sdd`/`sprint`), and `blockers`; re-run Flatline per blocker and verify each is resolved — if any remain, HALT with "Blocker not addressed: {id}". Otherwise resume from the phase the report names (`prd` → 1.4, `sdd` → 2.3, `sprint` → 2.5) and log a `flatline_resume` event with `original_run_id`, `phase`, `blockers_resolved`, and `timestamp`. If no escalation is found, check NOTES.md's "Flatline Halt" section and resume from the last checkpoint instead.

### Resume from Post-PR Context Clear

When the post-PR state file (`.run/post-pr-state.json`) shows `CONTEXT_CLEAR`: load the checkpoint from NOTES.md's Session Continuity section, confirm the PR is open, and continue with `.claude/scripts/post-pr-orchestrator.sh --resume` (fresh-context E2E). On success, set state to `READY_FOR_HITL` and continue to Phase 6 (if enabled) or Phase 7. On a repeated failure (circuit breaker: same failure twice), HALT; otherwise fix, retry, or escalate.
</resume_support>

<factual_grounding>
## Factual Grounding

ALL claims MUST be evidenced.

### Required Format

```markdown
✓ GROUNDED: "Function validates JWT tokens" (src/auth/jwt.ts:45)
✗ UNGROUNDED: The system probably handles auth well
✓ FLAGGED: [ASSUMPTION] Users likely prefer dark mode
```

### Verification

Before synthesizing: quote the exact source text, cite it with an absolute path and line, and flag assumptions explicitly.
</factual_grounding>

<trajectory_logging>
## Trajectory Logging

Log every significant action to `grimoires/{project}/trajectory/{date}.jsonl`:

```jsonl
{"ts":"2026-01-30T22:30:00Z","agent":"autonomous-agent","phase":0,"action":"preflight_start","status":"started"}
```

Required fields: `ts` (ISO 8601), `agent` (`"autonomous-agent"`), `phase` (current phase number), `action` (a verb), `status` (`started`/`completed`/`failed`/`escalated`). Optional: `skill`, `tokens_used`, `audit_score`, `remediation_loop`.
</trajectory_logging>
