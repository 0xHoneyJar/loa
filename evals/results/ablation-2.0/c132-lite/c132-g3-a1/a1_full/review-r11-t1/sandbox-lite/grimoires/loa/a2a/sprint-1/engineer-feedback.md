## Overall Assessment

The change under review is the cycle-126 sprint-247 PR "full-size adapters, Bridgebuilder and Flatline — every size decision derives from the resolved catalog entry" (65 files). The core of it is sound: `loa_cheval/routing/ceiling.py` is a clean, well-tested policy module (I1 output-budget fit, I2 probed/calibrated/derived/observed/guard bound, every basis named in the envelope); the adapters' temperature/beta-header/health-probe changes are correct and covered; the catalog, generated maps, Bridgebuilder registry and bats fixtures regenerate identically from the yaml (verified: `MODEL_MAX_OUTPUT` regenerated byte-for-byte; `dist/.build-manifest.json` hashes match every touched resource file). All runnable tests pass on a head overlay (25 pytest in the self-contained modules; 11 bats across `flatline-max-tokens`, `multipass-estimator`, `cost-report` CR-8, `loa-status-providers` LSP-5). The adapter-level pytest files could not be executed here because the workspace checkout is a later snapshot than this PR and its untouched modules import symbols the PR-era `types.py` lacks; those files were reviewed by reading.

Two defects block the merge. First, the per-hop walk gate re-estimates the input with the chars/3.5 heuristic after the pre-flight has already replaced that estimate with the provider's `count_tokens` answer, so a request the provider confirmed fits is refused as `ROUTING_MISS` on every HTTP hop. Second, Bridgebuilder's new default model `opus` is a catalog alias that the Bridgebuilder budget table cannot resolve, so the default review falls to the `default` truncation row (100K / 4096) — a regression from the 160K row the previous concrete id resolved to, in the PR whose purpose is to derive every size decision from the catalog entry. Five medium findings (head-only `_ceiling_unverified`, any-429 short-circuit, the retry shrink's lost typed error, the long-context threshold ignoring cache tokens, the Flatline 64K-per-voice budget) and several lows follow.

The implementation report carries no `## AC Verification` walkthrough (it is the PR title); under the eval's reduced-input rules that is recorded as a process gap, not counted.

## Changes Required

### 1. Functionality — the walk gate ignores the authoritative count (D-1.4)

- **HIGH** (confidence: high) `head/.claude/adapters/cheval.py:2118-2120` — the per-hop walk gate calls `estimate_tokens(messages)` afresh and compares the raw chars/3.5 (or cl100k) heuristic against `_input_threshold`, while the pre-flight at `head/.claude/adapters/cheval.py:1841-1843` has already replaced `_preflight_estimated` / `_walk_estimate` with the provider's `count_tokens` result (gate(): `head/.claude/adapters/loa_cheval/routing/ceiling.py:409-412`) and the I1 fit at `head/.claude/adapters/cheval.py:2097` consumes that count. Two different input numbers are compared against the same bound.
**File:** `head/.claude/adapters/cheval.py:2118`
**Issue:** English-prose prompts are where chars/3.5 over-counts (~4 chars/token). Concrete input: heuristic 190,000, provider count 166,000, probed bound 180,000. Pre-flight: 190K ≥ 0.9 × 180K → counter runs → 166K ≤ 180K → `dispatch`, envelope `estimated_input_tokens: 166000`, `estimator.method: count_tokens`. Walk gate on the head hop: `_lookup_max_input_tokens(...)` → 180,000; `estimate_tokens(messages)` → 190,000 > 180,000 → `ROUTING_MISS`; same on `claude-opus-4-8`; the chain lands on `claude-headless` (no HTTP ceiling) or exhausts with `CHAIN_EXHAUSTED`. The envelope then says "166000 estimated" beside `ROUTING_MISS` rows saying "190000 > 180000".
**Why This Matters:** D-1.4 ("near the bound the provider's count replaces the estimate") is the sprint's answer to the estimator's uncertainty; the walk gate silently un-does it, and the count_tokens round-trip is paid for nothing. The CLI-hop fallback also changes transport, cost and timeout class without any operator-visible reason.
**Required Fix:** Use one estimate in all three places: `_estimated = _walk_estimate if _walk_estimate is not None else estimate_tokens(messages)` at line 2119 (and in the `message_redacted` text), so the pre-flight count, the I1 fit and the walk gate agree. Add an e2e row to `test_ceiling_e2e.py` with heuristic > bound ≥ count asserting one dispatch and no `ROUTING_MISS`.

### 2. Functionality — Bridgebuilder's default model is an alias its budget table cannot resolve

- **HIGH** (confidence: medium) `head/.claude/skills/bridgebuilder-review/resources/config.ts:172` — `DEFAULTS.model` changes from the concrete `claude-opus-4-7` to the alias `opus`. The comment says the alias is "resolved by cheval's alias path", which is true for dispatch, but Bridgebuilder's own size decisions key on the model string: `getTokenBudget(model)` looks up `GENERATED_TOKEN_BUDGETS` (`head/.claude/skills/bridgebuilder-review/resources/core/truncation.generated.ts:19-52`), which carries only concrete ids and no alias table (no `GENERATED_MODEL_ALIASES` export exists at head), and the PR adds no alias resolution on the TS side.
**File:** `head/.claude/skills/bridgebuilder-review/resources/config.ts:172` (also `head/.claude/skills/bridgebuilder-review/resources/personas/quick.md:2` `# model: tiny`, `head/.claude/skills/bridgebuilder-review/resources/personas/security.md:2` `# model: opus`)
**Issue:** With the default config, `getTokenBudget("opus")` misses the generated twin and the hand table and returns `TOKEN_BUDGETS["default"]` = `{ maxInput: 100000, maxOutput: 4096, coefficient: 0.25 }`. The base default (`claude-opus-4-7`) resolved to the 160,000-input row; the head default resolves to 100,000 — a 37 % smaller review payload introduced by the PR that exists to size from the catalog. The `tiny` persona has the same problem (haiku row is 160K; `tiny` → 100K). The 32,000 maxOutput the new `truncation-registry.test.ts` asserts for the 5-family is never reached by the default model. Separately, `DEFAULTS.maxInputTokens: 200_000` (`config.ts:176`) exceeds the 5-family's probed bound (180,000) and the generated row (160,000); wherever the raw config value governs the prepared payload, cheval's gate preempts it with `CONTEXT_TOO_LARGE` under the default `probed` policy.
**Why This Matters:** The sprint's acceptance claim is "every size decision derives from the resolved catalog entry"; the Bridgebuilder default now derives from the fallback row instead. The PR's own tests only probe concrete ids (`truncation.test.ts`, `truncation-registry.test.ts`), so nothing fails.
**Required Fix:** Either (a) keep a concrete default (`claude-opus-5`) and let the catalog's alias retarget be mirrored by `gen-bb-registry.ts`, or (b) emit the yaml's `aliases:` block into `truncation.generated.ts` and resolve it in `getTokenBudget`/the input-budget clamp before the table lookup; add a test that `getTokenBudget("opus")` equals `getTokenBudget("claude-opus-5")`. Lower `maxInputTokens` to the generated row (160,000) or clamp it to `getTokenBudget(model).maxInput` for known ids.

## Observations

Non-blocking; none counted in the trailer except as medium/low.

### 1. Error handling — `_ceiling_unverified` is the head's status, applied to every hop

- **MEDIUM** (confidence: high) `head/.claude/adapters/cheval.py:1843` — `_ceiling_unverified` is assigned once from the head entry's pre-flight outcome and never recomputed in the chain loop, yet it selects the error class at `head/.claude/adapters/cheval.py:2256` (`CEILING_UNVERIFIED_LIMIT` vs `PROVIDER_CONTEXT_LIMIT`) and the non-walk short-circuit at `head/.claude/adapters/cheval.py:2297` for every fallback hop. Scenario: opt-in, head `claude-opus-5` dispatches 600K above its probed bound (unverified=True), fails with a walkable 503; the fallback is a calibrated entry (900K); its ordinary 429 now exits `RATE_LIMITED` with `calibration_needed` written for the fallback and a `RATE_LIMIT_UNVERIFIED` row appended for an entry that was never unverified. The converse (verified head, unverified fallback) mis-classes a provider verdict as `PROVIDER_CONTEXT_LIMIT`.
**Suggestion:** Compute the status per hop from the `input_bound` decision already made in `_lookup_max_input_tokens` (return the `CeilingDecision`, or recompute via `_ceiling_input_bound(_hop_entry, max_tokens=_hop_budget, observed=...)`): `unverified = policy == "derived" and not decision.calibrated and estimate > decision.probed`. Keep the head's flag for the envelope only.

### 2. Error handling — every 429 above the probed bound ends the call

- **MEDIUM** (confidence: high) `head/.claude/adapters/cheval.py:2297-2306` — the comment says "the token-limit class", but the arm fires on any `RateLimitError` while `_ceiling_unverified` is set; `RateLimitError` at head (`head/.claude/adapters/loa_cheval/types.py:225-229`) carries no token-limit discriminator and the adapter (`anthropic_adapter.py:343`, `:489`) discards the 429 body. A plain requests-per-minute 429 on the primary therefore exits `RATE_LIMITED` instead of walking to the declared fallback, writes a `RATE_LIMIT_UNVERIFIED` row keyed to the input size, and tells the operator to calibrate. Under the opt-in only, and arguably conservative (a 600K request plausibly is an ITPM hit), hence medium.
**Suggestion:** Parse the 429 body ("input tokens per minute" / "tokens per minute") into a `token_limited` flag on `RateLimitError` and gate the short-circuit on it; otherwise fall through to the existing `PROVIDER_OUTAGE` walk.

### 3. Error handling — the retry shrink can lose the provider's verdict

- **MEDIUM** (confidence: high) `head/.claude/adapters/loa_cheval/providers/retry.py:494-495` — the one-shot shrink does `request = replace(...)` then `continue` inside `for attempt in range(max_retries + 1)` without recording `last_typed_error = e` or `last_error`. When the `ProviderContextLimitError` arrives on the final iteration (`max_retries: 0`, or three transient 429/5xx failures first under the default 3, or the global attempt budget at `retry.py:355-365` trips), the `continue` falls out of the loop and `retry.py:527-532` raises `RetriesExhaustedError` with no typed cause. cheval's handler at `head/.claude/adapters/cheval.py:2338` then classes the hop `FALLBACK_EXHAUSTED` and walks the oversized payload to the next voice — the exact outcome D-1.1b forbids — with no observed-bound row and no `calibration_needed`. The shrunk request is also never sent.
**Suggestion:** Give the single shrink its own attempt outside the retry count (or `raise` instead of `continue` when `attempt == max_retries`), and set `last_typed_error = e` on that path. Add a retry test with `max_retries: 0`.

### 4. Metering — the long-context threshold ignores cache tokens

- **MEDIUM** (confidence: medium) `head/.claude/adapters/loa_cheval/metering/pricing.py:168` — `if threshold is not None and input_tokens > threshold`. The ledger passes Anthropic `usage.input_tokens`, which excludes `cache_read_input_tokens` / `cache_creation_input_tokens` (`anthropic_adapter.py:557-562`), while the premium is applied to `cr_cost` / `cw_cost` at `pricing.py:171-172` — the code treats cache traffic as input for the multiplier but not for the threshold. A request with 60K fresh and 180K cached tokens (240K prompt, premium-billed by the provider) is priced at base rates and `long_context` is not set, so `cost-report.sh long_context_rows` and the daily budget enforcer under-count.
**Suggestion:** Test `input_tokens + cache_read_tokens + cache_creation_tokens > threshold`, and say in the catalog comment which total the threshold applies to.

### 5. Flatline — 64K per voice re-opens the cycle-124 timeout hazard

- **MEDIUM** (speculative, confidence: low) `head/.claude/scripts/flatline-orchestrator.sh:1027` with `FLATLINE_VOICE_MAX_TOKENS_CAP=64000` at `:129` — review, skeptic and score calls on every 128K-declared entry now pass `--max-tokens 64000` where cycle-124 deliberately passed 16000 "so the 600 s per-call timeout never meets a 64K-output generation" (the removed comment). `DEFAULT_MODEL_TIMEOUT=120` (`:115`) is what `run_phase1` / `run_inquiry` pass (`:2599`, `:2661`). The scorer emits a small JSON array; on `claude-opus-5` adaptive thinking shares the budget, so the cap mostly lengthens a runaway generation into the timeout. `tests/unit/cycle-124-dispatch-budgets.bats:5-8` still states the opposite rationale in its header while the bullet below it was updated.
**Suggestion:** Keep the catalog-derived budget but let the mode supply a cap (score ≤ 16K), or raise the phase timeout to match; fix the bats header.
