## Overall Assessment

The change under review is the sprint-257 pull request (80 files): the per-provider insecure-endpoint opt-in and keyless providers on the cheval path, thinking-trace stripping and `response_format` on the OpenAI chat path, catalog price provenance and the catalog-priced dissent budget gate, advisory voices, the `hounfour.locality: local_voices` posture across the dissent, Flatline, Bridgebuilder and the health probe, and Bridgebuilder's trusted configuration and DEGRADED exit code.

Most of it is careful work and the tests back it: on an overlay of the head files, all 123 new Python tests pass and all 50 new bats cases pass (the three cases that failed on the first run were caused by `/tmp` being mounted `noexec` on this host, not by the change). The endpoint rule itself (`check_insecure_optin`, `validate_declared_endpoint`, `TransportPolicy`) is sound and the case table holds on both paths.

The blocking problem is the `local_voices` posture: it trusts the `dispatch_group: local` label and never checks that the provider's endpoint is actually loopback, RFC1918 or `localhost`, so a hosted https provider labelled `local` is planned, dispatched and audited as local (demonstrated below). The second blocking problem is that Bridgebuilder's trusted configuration gates only which voices are planned; cheval still reads the checkout's `.loa.config.yaml` for the endpoint and credential at dispatch, so the SKILL.md claim that the keys "follow the trusted-source precedence even when the checkout is a PR head" is not what the code delivers. Six medium and eight low observations follow, including the dissent's own findings, triaged against the head files.

Process: `reviewer.md` is the PR title alone and carries no `## AC Verification` walkthrough (automatic CHANGES_REQUIRED per the skill, independent of the findings), no fast-gate evidence (`tsc --noEmit`, `npm test`) for the rebuilt `dist/`, and the change touches no CHANGELOG while README.md:22 points at one. Bridgebuilder's TypeScript tests could not be run here (no `node_modules` in the snapshot).

**Verdict:** CHANGES REQUIRED

## Changes Required

### 1. Locality — the `dispatch_group: local` label is trusted, the endpoint host is never checked

- **HIGH** (confidence: high) `head/.claude/scripts/lib/hop-locality.py:116` — a provider with `endpoint: https://api.acme.example/v1`, `auth: "{env:ACME_KEY}"` and a model marked `dispatch_group: local` is classified `local` (`lr	acme	local	dispatch_group=local`, reproduced with the head classifier against the head catalog), so under `hounfour.locality: local_voices` adversarial-review.sh and flatline-orchestrator.sh plan the hop, cheval sends the prompt to `api.acme.example`, and the MODELINV row records `hop_locality: local` with `destination.host: api.acme.example`.
**File:** `head/.claude/scripts/lib/hop-locality.py:116-121`, `head/.claude/skills/bridgebuilder-review/resources/config.ts:726-732`, `head/.claude/adapters/loa_cheval/audit/modelinv.py:473-476`, `head/.claude/adapters/loa_cheval/config/endpoint_policy.py:172`
**Issue:** All three classifiers (`classify`, `isLocalVoice`, `hop_locality_of`) decide locality from the `dispatch_group` string alone. `validate_providers` requires only that a keyless provider's models declare *some* `dispatch_group`; nothing refuses `local` on a provider whose endpoint host fails the same loopback/RFC1918/`localhost` rule the opt-in already encodes (`check_insecure_optin`). The module docstring of hop-locality.py promises "Fail closed — a hop is never called local because it could not be read", but a hop *is* called local because a label said so.
**Why This Matters:** FR-8's whole promise is "a local posture keeps model calls local". One typo or one hostile config line defeats it silently, and the audit trail then asserts the opposite of what happened. Under `local_voices` the posture is the only control: the opt-in rule does not fire for an https public endpoint.
**Required Fix:** Define the local-hop rule once — the hop's provider is an HTTP provider (not `*-headless` / `kind: cli`) whose endpoint host passes `check_insecure_optin`'s host acceptance — and apply it in `validate_providers` (refuse a `local` label the endpoint cannot honour at load), in hop-locality.py (stdlib mirror, reason `endpoint_not_local:<host>`), in `isLocalVoice` (carry `endpoint` in `ProviderDecl`) and in `hop_locality_of`. Add the mislabelled-provider case to `test_config_examples_load.py`, `adversarial-review-locality.bats` LOC-7 and `trusted-config.test.ts`.
**Reference:** CWE-807 (Reliance on Untrusted Inputs in a Security Decision); SDD D-8.0 / D-8.1.

### 2. Bridgebuilder trusted configuration gates admission only; dispatch still reads the checkout

- **HIGH** (confidence: medium) `head/.claude/skills/bridgebuilder-review/resources/config.ts:685` — on a pull request the head-only refusal compares the *presence* of `allow_insecure_endpoint` (`insecure` is a boolean) and of `keyless`, never the endpoint or the credential; a head that keeps `keyless: true` and an opt-in on a trusted provider but re-points `endpoint` to another private host, or drops `keyless` in favour of `auth: "{env:OPENAI_API_KEY}"` on an https endpoint, is admitted (`validateApiKeys` reads the trusted view, config.ts:398) and then dispatched by cheval with the head's endpoint and credential.
**File:** `head/.claude/skills/bridgebuilder-review/resources/config.ts:684-685`, `head/.claude/skills/bridgebuilder-review/resources/main.ts:459-464`, `head/.claude/skills/bridgebuilder-review/resources/core/multi-model-pipeline.ts:224`, `head/.claude/skills/bridgebuilder-review/SKILL.md:118`
**Issue:** `config.trusted` is consulted only in `validateApiKeys` and the pipeline's keyless check. Every voice goes through `ChevalDelegateAdapter`, which runs `.claude/adapters/cheval.py` from `process.cwd()`; cheval's loader reads the working tree's `.loa.config.yaml` (`hounfour.providers`, `aliases`, `secret_env_allowlist`) for the actual endpoint, auth template and alias target. The trusted view is never handed to cheval, and the drift between head and trusted config is never computed.
**Why This Matters:** SKILL.md:118 now states that the provider, locality and exit keys "follow the trusted-source precedence below even when the checkout is a PR head", and the tests model the working tree as the PR head. Under that model a PR can route the reviewed diff — and, via an in-allowlist `{env:VAR}` auth, a runner credential — to an endpoint of its choosing while the startup line says "Trusted config: base-ref". The exposure predates this change when the checkout is a PR head (#1050 closed it as not-applicable to the shipped invocation model), but this change claims to close it and does not.
**Required Fix:** Either (a) refuse the multi-model run on a pull request whenever the head's `hounfour.providers`, `hounfour.aliases`, `hounfour.locality` or secret allowlist differ from the trusted view (a distinct exit code, named in SKILL.md), or (b) pass the trusted config to cheval (a `LOA_CONFIG_PATH_OVERRIDE`-style path written from the trusted text) so the dispatch reads what the gate read. Compare the opt-in *host* and the endpoint, not a boolean. State the invocation model the protection assumes in SKILL.md.
**Reference:** CWE-345 (Insufficient Verification of Data Authenticity); OWASP A08:2021 Software and Data Integrity Failures; SDD D-7.5, DEC-0170.

## Observations

### 1. Locality posture — enforcement gaps (medium)

- **MEDIUM** (confidence: high) `head/.claude/adapters/cheval.py:1813` — cheval plans around the agy opt-in (`_plan_around_agy`) but never around `hounfour.locality: local_voices`; it only *records* `locality_mode` (cheval.py:2195, 3031). A direct `cheval invoke --model gpt-5.5`, or any caller other than the four patched planners, dispatches a hosted hop under the posture, and a local alias whose catalog `fallback_chain` names a hosted entry is walked inside the one call (head has no load-time fallback check; only hop-locality.py's planner-side check, which cheval does not consult). The dissent's DISS-002 raises the same gap, though it cites a `validate_local_fallbacks` that exists only in a later tree, not in head.
- **MEDIUM** (confidence: high) `head/.claude/adapters/cheval.py:541` — `ModelConfig.dispatch_group` is read from the model entry only, so a provider-block `dispatch_group: local` is honoured by hop-locality.py:116 and config.ts:730 (planned as local) but not by `OpenAIAdapter._transport_policy` (openai_adapter.py:221: no TransportPolicy without an opt-in — proxy env honoured, urllib follows 3xx, no path-prefix rule) nor by `hop_locality_of` (modelinv.py:475: `hosted`). One hop, three answers. (Dissent DISS-001 / DISS-C-001, confirmed against head; their "https loopback without opt-in" scenario cannot load in head — `ENDPOINT-IP-BLOCKED` — but a public https endpoint with the block-level label can.)
- **MEDIUM** (confidence: high) `head/.claude/skills/bridgebuilder-review/resources/config.ts:732` — `isLocalVoice` ignores the model's `fallback_chain` (hop-locality.py refuses a local entry whose chain reaches a hosted model: LOC-7) and returns `local` for a model id the provider never declares when every declared model is local (`isLocalVoice("local-vllm", "unlisted-alias")` is asserted `true` in trusted-config.test.ts). ### 2. Budget gate (medium)

### 3. Health probe for configured providers (medium)

### 5. Low
