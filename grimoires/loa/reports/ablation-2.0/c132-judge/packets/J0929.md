head/evals/harness/ablation-report.py:1082 — [HIGH] The grader_versions sort key splits each version on "." and turns only all-digit parts into int, so two versions that differ in a non-numeric part make Python compare str with int and raise TypeError. Examples: "1.2.13" vs "1.2.13-rc1", or a "v1.2" tag. I reproduced this by calling batch_record on two run dirs whose grade.json hold 1.2.13 and 1.2.13-rc1: it raised "TypeError: '<' not supported between instances of 'str' and 'int'". Only Fail is caught, so a grade.json value the agent can influence kills the whole report with a traceback. The header promises the batch record is "never fatal". A total-order key is needed, e.g. (0, int) / (1, str) tuples per part.

Such rows count as "no suite_version". When only one other version is present they are silently pooled into it (line 853). Reproduced: rows with suite_version 2 and 2.5 come back from partition() as one group {'2': 2 rows}, which breaks the "never pooled" guarantee. The docstring also says 1, 1.0 and "1" are one version, but the string "2.0" stays a separate key from 2. Non-integer floats should map to their own key (or be refused), and numeric strings should be normalised the same way as numbers.
