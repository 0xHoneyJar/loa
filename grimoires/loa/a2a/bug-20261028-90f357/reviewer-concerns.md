# Reviewer concerns — sprint-bug-283 (bug 20261028-90f357, KF-064)

Scope: `git diff 46962aab0..f2b3d97e9 -- .claude/scripts/post-merge-orchestrator.sh tests/unit/post-merge-publication.bats` — one red/fix pair. The publisher's release phase compared the GitHub read-back body with the sent notes by exact equality; GitHub stores a literal `\u00XX` escape of a C0 control or DEL as caret notation (`\u0000` → `\^@`, `\u001f` → `\^_`), so the v2.0.0-rc.9 publish failed after creating the release and the retry failed identically. The fix normalises BOTH sides with that one rewrite before comparing; the other identity terms stay exact. Please attack:

1. Is the normalisation a faithful model of GitHub's rewrite? Does GitHub rewrite anything else in release bodies that a body could legitimately contain (CRLF, trailing whitespace, `\r`, other escape families such as `\x00`, `\0`, HTML entities, ` `)? A body difference the normaliser cannot explain still fails — is that the right default for a publisher (fail closed) versus a WARN?
2. Security: can the tolerance let a DIFFERENT release pass as identical? A pre-existing release whose body differs only in the normalised region (e.g. it contains `\^@` where the candidate has `\u0000` — the same thing after normalisation) is accepted by design; is there a body the normaliser maps onto the candidate's that an attacker who can edit the GitHub release could use to smuggle different notes? (The regex is a one-way, length-shrinking map on a 6-char pattern.)
3. The python3 dependency: `python3 -I -c` in a publication path — the surrounding script already uses python3 for jcs-helper; failure modes when python3 is missing (the transform fails → both sides empty? → `$sent != $read` false → PASS?). Check: `sent_norm=$(release_body_normalize <<< "$notes")` under `set -e`/pipefail — if python3 is absent, does the comparison degrade to accepting anything? Should an empty normalised result for a non-empty input refuse?
4. `<<< "$notes"` appends a newline; `$(...)` strips trailing newlines on both sides — symmetric? The read side goes through `jq -r '.body // ""'` then the normaliser then `$(...)`; the sent side `<<<` then `$(...)`. A body ending in several newlines: both sides lose all trailing newlines — equal; but is a body with internal `\r\n` preserved identically on both paths?
5. The failure message now lists the mismatching terms and lengths — any information disclosure concern (bodies are public release notes)? Does any test grep the exact old reason string?
6. The test stub's rewrite (`GH_BODY_REWRITE=caret`) is the same regex as the fix — a tautology risk: if the regex were wrong in the same way on both sides the test would still pass. The real-world check (the rc.9 candidate body vs the stored GitHub body) was done by hand outside the suite; should a fixture carry the real pair?
7. Case B pins "any other body difference refuses" with one appended line; is a difference INSIDE the normalised region (e.g. `\^A` vs `\u0000`) also refused?
