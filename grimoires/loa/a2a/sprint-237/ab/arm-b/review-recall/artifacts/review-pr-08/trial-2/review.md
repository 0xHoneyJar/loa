# Review: chore(ledger,tools,cheval): lighter ledger content check, simpler heredoc skipping, fewer except clauses

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:157` — the content guard was weakened from `jq -es 'length == 1 and (.[0] | type == "object")'` (single JSON object) to a bare `jq empty` (any valid JSON). This reopens the exact bug class the guard exists to prevent (bug 20260808-a008c6, cited verbatim in the comment directly above the weakened line). `_write_ledger "null"` now passes the guard (`null` is valid JSON), and at line 179 `jq '.last_updated = $ts'` auto-vivifies `null` into `{"last_updated": "<ts>"}` — a non-empty result, so it also passes the `[[ -z "$updated_content" ]]` check at line 180 and gets written atomically over the real ledger, silently destroying `version`, `cycles`, `next_sprint_number`, and `active_cycle`. Any caller that ends up passing a literal `"null"` string (e.g. a `get_active_cycle`/`jq -r '... // "null"'` result threaded into `_write_ledger` by mistake, or any future refactor) now truncates the ledger with zero error output, exactly like the original empty-string bug it replaces. Non-object-but-non-null values (arrays, scalars, booleans) are still caught downstream because `.last_updated = $ts` errors on them, but `null` slips through silently. Verified locally: `echo 'null' | jq empty` exits 0, and `echo 'null' | jq '.foo = "bar"'` produces `{"foo":"bar"}`.

- **HIGH** (confidence: high) `head/tools/check-no-swallowed-jq.sh:138-146` — the heredoc-skip logic dropped the `hd_exec` distinction entirely (previously: only skip heredoc bodies that are *not* being fed to an interpreter — i.e. fixture/doc text — while still scanning heredoc bodies piped to `bash`/`sh`/`python`/etc. or otherwise executable). The new `in_heredoc { ... next }` block unconditionally skips every line inside *any* heredoc, executable or not. This is a real detection-surface regression, not just a false-positive fix: any gate-critical script (the `ENFORCED_FILES` set: adversarial-review.sh, flatline-orchestrator.sh, scoring-engine.sh, post-pr-triage.sh, red-team-*) that builds an inline sub-script via `bash <<EOF ... jq ... || echo default ... EOF` or `... | python3 <<EOF`, and swallows a jq failure inside that heredoc, is now invisible to the tripwire this PR's own header comment describes as guarding against "KF-004 (zero-findings canonical verdicts masking real findings, recurrence ≥20) and KF-015 (silent-clean red-team gate pass, 4/4 sprints)". The PR description frames this as "simpler heredoc skipping" but it silently narrows what the scanner catches on the exact class of scripts it exists to protect.

- **HIGH** (confidence: medium) `head/.claude/adapters/loa_cheval/providers/agy_headless_adapter.py:157-165` — removing the `except ValueError` handler (previously converting an embedded-NUL argv failure into `ProviderUnavailableError` so the fallback chain advances) breaks the explicit design invariant stated in the adjacent, still-present `except OSError` comment: "WALK the chain, never crash with a raw OSError." `ValueError` from the same `run_subprocess_pgkill`/exec call (raised by CPython on embedded NUL bytes in argv) is a sibling failure mode, and it is now unhandled — a prompt containing a NUL byte raises an uncaught `ValueError` out of `_execute_impl` instead of failing over to the next provider, and (depending on the caller above this adapter) can abort the whole cheval multi-model run rather than just this one provider. Confidence is medium rather than high because I did not find a concrete producer of NUL bytes in `_build_prompt(request.messages)` in this diff's scope — but the handler's own removed error message ("embedded NUL in the prompt?") shows it was added for a real, previously-observed case, and the PR gives no justification for why that case no longer applies.

## Observations

- **MEDIUM** `head/.claude/scripts/ledger-lib.sh:157` and `:179` — `echo "$content"` replaces `printf '%s' "$content"`. Bash builtin `echo` can interpret leading `-n`/`-e`/`-E` as options (behavior varies with `xpg_echo`/`posix` shopts) and may special-case backslash escapes depending on shell mode, whereas `printf '%s'` is a hard literal pass-through. Ledger content is JSON starting with `{` in the normal path, so this is unlikely to bite today, but it's a needless portability regression paired with the point above where content shape is exactly what's under discussion.

- **LOW** `head/.claude/scripts/ledger-lib.sh:152-156` — the comment above the guard still describes the truncation bug in detail but was not updated to reflect that the object-type check was dropped; a future reader skimming the comment would assume the guard still enforces "non-object" rejection, which it no longer does (see HIGH finding above).
