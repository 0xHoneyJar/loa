# Review: chore(cheval,flatline,constructs): remove spawn-failure handlers, skeptic normalization and membrane overlays

## Summary

This PR bundles three unrelated removals across three subsystems: (1) two exception handlers in
the claude-headless provider adapter, (2) a JSON envelope-normalization helper in the flatline
skeptic pipeline, and (3) event/composition overlay support in the construct index generator. All
three removals are framed as reverting to a simpler "manifest-only" / prior form, but each one
removes defensive handling that was added to close specific, documented failure modes, and none
of the removals are explained beyond the commit title. I could not find corresponding test or
caller updates in this diff to show the removed behavior is dead code — on the evidence available,
all three are live regressions.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/adapters/loa_cheval/providers/claude_headless_adapter.py:178-192` — Removing the `except OSError` and `except ValueError` handlers (base had them at the equivalent location) means spawn-level failures other than `FileNotFoundError` — `ENOMEM`, `E2BIG`/ARG_MAX, and `ValueError` from an un-executable argv (e.g. embedded NUL in the prompt) — now propagate as raw, undocumented exceptions out of `run_subprocess_pgkill(...)` instead of being converted to `ProviderUnavailableError`. Every other failure path in this same function (timeout, output-cap-exceeded, semaphore-exhausted, `FileNotFoundError`) is deliberately converted to `ProviderUnavailableError`/`ConfigError` specifically so the cheval fallback chain can catch it and advance to the next provider (see the adjacent comment at head/.claude/adapters/loa_cheval/providers/claude_headless_adapter.py:183-186, "C12 closure: distinct exit class so ... the caller routes the failure separately"). With this removal, a transient spawn failure (e.g. hitting `ARG_MAX` with a large prompt, or `ENOMEM` under load) will now raise an unhandled `OSError`/`ValueError` instead of triggering fallback — likely crashing the whole consensus/flatline invocation rather than degrading to the next model in the chain. This directly regresses the failure-isolation guarantee the surrounding code exists to provide.

- **HIGH** (confidence: medium) `head/.claude/scripts/flatline-orchestrator.sh:1594-1598,1624-1627` — `normalize_skeptic_envelope` (present in base at the equivalent location, immediately after `extract_json_content`) coerced a skeptic model's JSON output into the canonical `{"concerns": [...]}` shape even when the model returned a bare array or a scalar, and hard-defaulted to `{"concerns":[]}` on any `jq` failure. `extract_json_content` (head/.claude/scripts/flatline-orchestrator.sh:261) only extracts and de-fences/de-BOMs the `.content` string — it does not enforce or coerce the resulting JSON's top-level shape. With the normalizer removed, a skeptic response shaped as a JSON array (which is exactly the case the removed function's `elif type == "array"` branch existed to handle) is now written to `*-skeptic-prepared.json` unchanged and passed via `--skeptic-gpt`/`--skeptic-opus`/`--skeptic-tertiary` to the consensus step. A downstream `jq '.concerns'` (or equivalent) against a top-level array raises `jq: error: Cannot index array with string "concerns"`, which is worse than the missing-concerns case the removed code specifically guarded against. Since the consensus consumer script isn't part of this diff, I can't confirm it now tolerates array-shaped input — absent that evidence this is a functional regression in the skeptic path, not a no-op cleanup.

- **HIGH** (confidence: medium) `head/.claude/scripts/construct-index-gen.sh:302-303,396,414-423` — Three related behaviors are dropped simultaneously with no fallback: (a) event field extraction narrows from `(.name // .event // .type)` / `(.event // .name // .type)` to `.name` only (emits) and `.event` only (consumes) — a manifest whose events use `event`/`type` keys instead of `name` now silently emits an empty `events.emits`/`events.consumes` list (the `// empty` drops the entry rather than failing loud); (b) the `construct.yaml` overlay's own `events.emits`/`events.consumes` override (removed `cy_emits`/`cy_consumes` block) is dropped entirely, so an author who intentionally overrides manifest-declared events in `construct.yaml` is now silently ignored; (c) `compose_with` declared explicitly in `construct.yaml` (`.compose_with[].slug`) is discarded — `composes_with` is now hard-set to `[]` at construction (line 396) and later computed *purely* from read/write overlap (line 414's `compute_composition`, which used to be unioned with the manifest/overlay-declared list via `+ ($current.composes_with // [])`). Any construct pair that composes for a reason other than a literal write/read path match (e.g. event-based or convention-based composition) loses that relationship in the generated index with no warning. Since `.run/construct-index.yaml` is consumed for gating/composition decisions elsewhere in the framework (per the header comment "Sources: cycle-051, Sprint 103"), this is a silent data-loss regression on the index, not a pure revert of dead code.

## Observations

- `head/.claude/adapters/loa_cheval/providers/claude_headless_adapter.py:178-182` — `FileNotFoundError` (a subclass of `OSError`) is still caught explicitly and correctly precedes the (now-removed) generic `OSError` handler in ordering, so at least the most common spawn failure (missing binary) still degrades gracefully. It's specifically the *other* `OSError` subtypes that regress.
- None of the three removed behaviors have an accompanying test change in this diff (no test files are touched at all). If tests elsewhere already assert the old behavior (e.g. array-shaped skeptic envelopes, non-`name`-keyed events, or explicit `compose_with`), they should now be failing; if no such tests exist, that's itself a gap this PR should have closed rather than widened by removing the code they'd have covered.
- The PR description asserts these are reverts to "the manifest-only form" / removal of "extra" handlers, but gives no reasoning (issue link, incident, or measured cost) for *why* the removed behavior is undesired. Given each removed piece has a specific, commented rationale in `base/` (cycle/issue references for the adapter handlers, the explicit array-coercion branch for the skeptic normalizer, the overlay/compose_with merge logic), the burden is on the PR to explain what problem the removal solves; as written it reads as an unreviewed regression bundle across three unrelated files rather than a single coherent change.

## Overall Assessment

Three independent HIGH-severity regressions, each removing failure-mode handling that has a
documented reason to exist in `base/`, with no replacement logic, no caller adjustments, and no
test changes to show the removed paths are unreachable. Recommend rejecting and asking for either
(a) evidence the removed code paths are genuinely dead/wrong (e.g. the spawn errors can't actually
occur, the skeptic model never emits arrays, construct.yaml overlays for events/compose_with are
unused in the wild), or (b) splitting this into three separate, individually-justified PRs.
