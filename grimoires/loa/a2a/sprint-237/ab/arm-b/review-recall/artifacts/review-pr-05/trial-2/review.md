Scope note: no sprint plan / beads / `grimoires/loa/a2a/` context exists for this workspace. This is a standalone PR review against `PR.md` + `head.diff` + `base/`/`head/` snapshots, per `REVIEW-INSTRUCTIONS.md`. No AC Verification section applies.

## Changes Required

- **CRITICAL** (confidence: high) `head/.claude/hooks/safety/block-destructive-bash.sh:807` — the find-exec root capture now takes only `find`'s first positional argument as the "root" to validate, silently dropping the old code's handling of multiple positional roots. Concretely: `find ./safe /etc -exec rm -rf {} +` is a placeholder-only `rm` (`-rf`, `{}`, `+` are all skipped/placeholder tokens), so the segment is classified purely on `_seg_find_root`. The regex at line 776 (`find[[:space:]]+([^;&|)[:space:]]+)[^;&|)]*-exec$`) captures group 3 as `./safe` only — `/etc` is silently absorbed by the trailing `[^;&|)]*` before `-exec`. `./safe` matches `_re_allow_list` (`^\./[^/*.][^*]*`), so the whole segment is treated as safe and the command falls through to `exit 0` (allowed), even though it recursively `rm -rf`s everything `find` discovers under `/etc` as well. On `base/.claude/hooks/safety/block-destructive-bash.sh:800-807` (pre-change), the same command is caught: the old code tokenized the full span between `find` and `-exec`, counted the number of leading non-flag tokens (2, for `./safe` and `/etc`), and blanked `_seg_find_root` whenever that count was `!= 1` — which routed the segment into the ambiguous per-arg ladder (`{}`/`+` match none of the allow/block patterns) and produced `FR-2-AMBIGUOUS` (blocking exit 2). The new comment at lines 772-775 only documents the "flags before root" gap (`find -L root -exec`, still safely ambiguous) — it does not mention, and the diff does not preserve, the multi-root safety net. This is a real bypass of the hook whose entire purpose is to catch `find … -exec rm` patterns, reachable with an ordinary two-argument `find` invocation, not an exotic shell trick.
- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:79-89` — `get_completed_sprints` now counts every `${a2a_dir}/sprint-*` directory carrying a `COMPLETED` marker (`find "${a2a_dir}" -maxdepth 1 -type d -name "sprint-*"`), with no filtering to the numeric range that `get_total_sprints` (`workflow-state.sh:70-76`, `grep -c "^## Sprint [0-9]"` against the *current* `sprint.md`) actually scopes. The two functions are used together at `workflow-state.sh:144-148` (`[[ "${completed_sprints}" -ge "${total_sprints}" ]] && … STATE_COMPLETE`) and again at `workflow-state.sh:366-367` for the progress display (`Sprints: N/M complete`, `progress_percent`). Any non-numbered sprint directory that persists under `a2a/` — a bug-fix sprint (the framework's own convention names these `sprint-bug-<n>`, e.g. `sprint-bug-102`, per `.claude/rules/skill-invariants.md`'s "Origin" section) or a leftover/archived sprint from a prior cycle that shares the `a2a/` directory — now inflates the numerator without inflating the denominator. Concretely: `sprint.md` declares 2 numbered sprints (`total_sprints=2`), sprint-1 is still in progress, but two prior `sprint-bug-*` directories both carry `COMPLETED` markers → `completed_sprints=2 >= total_sprints=2` → `determine_state` incorrectly reports `STATE_COMPLETE` (and the `--json`/pretty-printed progress line reports "2/2 complete", 100%) while the actual numbered sprint plan is nowhere near done. The old code (`base/.claude/scripts/workflow-state.sh:76-84`) avoided this by iterating `1..total` and checking `a2a_dir/sprint-${i}/COMPLETED` directly, keeping numerator and denominator on the same numbering scheme.
