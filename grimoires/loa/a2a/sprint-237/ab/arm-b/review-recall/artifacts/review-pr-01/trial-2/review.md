# Review: chore(hooks,scripts): simplify carrier-value regexes, redaction patterns and sprint counting

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/lib/invoke-diagnostics.sh:50` — `redact_secrets()` narrows AWS key redaction from seven prefixes (`AKIA|ASIA|AROA|AGPA|AIPA|ANPA|ANVA`) down to `AKIA` only. `ASIA*` (STS temporary/session credentials — arguably the most common AWS credential to end up in ad-hoc logs since they're minted per-session), `AROA*` (role IDs), and the other four prefixes now pass through `redact_secrets` unredacted. Any `model-invoke` failure log captured via `setup_invoke_log`/`log_invoke_failure` that contains one of these non-AKIA credentials will write it to a temp file (and to any stdin piped through `redact_secrets` elsewhere) in the clear. The PR description frames this as "trimmed back to the documented AWS access-key shape," but the doc comment being trimmed to match is itself part of this diff (`head/.claude/scripts/lib/invoke-diagnostics.sh:37`) — it doesn't reflect a pre-existing spec, it retroactively justifies dropping coverage that was already shipped and working in `base/.claude/scripts/lib/invoke-diagnostics.sh:47`.

- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:72` — `grep -c PATTERN FILE` prints the match count to stdout even when the count is `0`, but still exits with status `1` when zero lines matched (standard grep behavior: "exit status 1 if no lines were selected"). The new one-liner `grep -c "^## Sprint [0-9]" "${SPRINT_FILE}" 2>/dev/null || echo "0"` therefore emits **both** grep's own `"0"` stdout line **and** the `echo "0"` fallback whenever `sprint.md` exists but contains zero `## Sprint N` headings — the function's stdout becomes the two-line string `0\n0` instead of `0`. Every caller treats the result as a single integer: `total_sprints=$(get_total_sprints)` is used in `[[ "${total_sprints}" -gt 0 ]]` (`workflow-state.sh:151`), `for i in $(seq 1 "${total_sprints}")` (`workflow-state.sh:158`, `:376`), and interpolated raw into the JSON heredoc as `"total_sprints": ${total_sprints},` (`workflow-state.sh:403`), which becomes syntactically invalid JSON (`"total_sprints": 0\n0,`) once `total_sprints` holds two lines. This breaks `/loa` status / `--json` output and any `jq` consumer the moment a project has a sprint plan file with no `## Sprint N` sections yet (e.g., right after `/sprint-plan` scaffolds the file, or any malformed/renamed heading). The base version's `n=$(grep -c ... || true); echo "${n:-0}"` avoided this because command substitution captures grep's stdout regardless of its exit code, and the explicit `echo "${n:-0}"` was the only thing printed.

- **HIGH** (confidence: medium) `head/.claude/hooks/safety/block-destructive-bash.sh:210-212` — removing `_bdb_re_tail` (base: `.claude/hooks/safety/block-destructive-bash.sh:216-217`, deleted along with its `while` loop at `base/.claude/hooks/safety/block-destructive-bash.sh:236-248`) together with loosening the prefix classes from `[^;&|'\"]*` to `[^;&|]*` reintroduces the exact multi-flag bug this file's own history (`bd-bdb-quote-blindness-pt1g`, referenced in the surrounding comments) was built to close. With quotes no longer excluded from the prefix, `[^;&|]*` in `_bdb_re_git`/`_bdb_re_brbd`/`_bdb_re_gh` can now consume straight through an earlier quoted value; under POSIX leftmost-longest ERE semantics (glibc regex, used by bash `[[ =~ ]]`), the match extends to the **last** `-m`/`-d`/`--body`/`--title` occurrence in the segment, so only that final quoted value is captured and redacted by `_bdb_scrub`. Any earlier `-m`/`-d`/`--body` value in the same segment is folded into the matched prefix and left byte-for-byte in `_cmd_match` — unredacted. The everyday two-part commit message `git commit -m "Title" -m "Body"` (a documented, common git convention for title+body messages) is exactly this shape: with two or more `-m` flags, only the body gets scrubbed, and the title stays live text subject to every subsequent `_match`/`_match_ci` pattern (P1–P12, FR-1.x). A commit titled e.g. `git branch -D cleanup` or mentioning `DROP TABLE` as prose would now trip a false BLOCK on a perfectly safe commit — the tail loop existed specifically to prevent this class of false positive across repeated flags. No compensating fix for the multi-flag case ships in this diff.

## Observations

- **LOW** (confidence: medium) `head/.claude/scripts/lib/invoke-diagnostics.sh:48` — the `Bearer` redaction character class dropped `=` (`[A-Za-z0-9=._-]+` → `[A-Za-z0-9._-]+`). Base64-padded bearer tokens ending in `=`/`==` will only have the portion before the first `=` redacted, leaving the padding characters (not secret material by themselves) trailing in the output. Low impact since `=` at the end of base64 carries no entropy, but it's an unexplained narrowing with no corresponding note in the "Expanded patterns" doc comment.

## Overall Assessment

Two of the three findings are outright correctness regressions with concrete, everyday reproduction cases (a sprint plan with no sprint headings yet; a two-part `git commit -m/-m`), not edge cases — both were working correctly in `base/`. The third (AWS prefix narrowing) is a silent security-coverage loss dressed up by a comment this same PR adds to make the narrower behavior look intentional/pre-existing. None of these are described in the PR summary, which characterizes the change as low-risk cleanup ("regexes lose their extra prefix classes", "redaction set is trimmed back", "restores the one-line sprint count") — each of those phrases is the bug.

Requesting changes: restore the dropped AWS key prefixes (or justify their removal with actual evidence they're out of scope), fix `get_total_sprints()` to emit exactly one line on the zero-match path (e.g. keep the `local n; n=$(... || true); echo "${n:-0}"` form, or `grep -c ... || printf '0'` is still wrong for the same reason — capture then default), and either restore the tail-loop/multi-flag handling in `block-destructive-bash.sh` or provide an equivalent fix for the `-m ... -m ...` case before merging.
