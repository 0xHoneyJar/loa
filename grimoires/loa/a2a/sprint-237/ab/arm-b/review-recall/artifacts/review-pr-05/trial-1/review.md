# Review: refactor(hooks,cheval,state): single-token find roots, plain 4xx handling, historical sprint counting

Three unrelated changes bundled in one PR (safety-hook regex, provider error
classification, sprint-count script). Reviewed each independently against
`head/`.

## Changes Required

- **CRITICAL** (confidence: high) `head/.claude/hooks/safety/block-destructive-bash.sh:776` — the new `_re_find_exec_prefix` only ever captures **one** token (`[^;&|)[:space:]]+` stops at the first whitespace) as the find root, and the caller (`head/.claude/hooks/safety/block-destructive-bash.sh:807`, `_seg_find_root="${BASH_REMATCH[3]}"`) trusts that single token as *the* root to classify. `find` accepts multiple starting paths, so a command like `find ./build / -exec rm -rf {} \;` captures only `./build` (which matches `_re_allow_list` at line 874/904 and is silently allowed) while the second, catastrophic root `/` is never inspected or classified at all — the rm invocation's own args are pure find-exec placeholders (`{}`), so the `_seg_placeholder_only` branch (lines 850-878) is taken instead of the per-arg ladder that would otherwise have caught `/`. The net effect is a full bypass of the destructive-rm guard for any `rm -rf` reachable via a multi-root `find ... -exec`, by prefixing one innocuous allow-listed path before the real target.
  This is a functional regression versus the old code (`base/.claude/hooks/safety/block-destructive-bash.sh:806-813`), which counted *all* leading non-flag tokens and reset `_seg_find_root=""` (disabling the find-root fast path) whenever there was more than one — falling back to the per-rm-arg ladder, which treats an unrecognized bare `{}`/`;` placeholder as ambiguous and blocks. The old code was overly conservative for legitimate multi-root finds, but it never silently allowed a smuggled dangerous root. The new comment at lines 772-775 documents "flags before root" as a known gap but does not mention (or intend, per the PR description) that *additional root arguments* are silently dropped from validation — that's a different, more serious gap than the one called out.
  Fix: only take the single-token fast path when `find`'s argument list contains exactly one leading non-flag token before the first `-flag`/`(`/`!` (i.e., restore the old token-counting loop, or extend the regex to reject/flag additional bare tokens before the first flag), falling through to AMBIGUOUS otherwise as before.

- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:79-91` — `get_completed_sprints` now globs every directory under `a2a/` matching `sprint-*` with a `COMPLETED` marker, completely decoupled from `get_total_sprints` (`head/.claude/scripts/workflow-state.sh:70-76`), which counts only `## Sprint N` headers in `sprint.md`. This repo's own conventions use non-numbered sprint directories such as `sprint-bug-102` (see `.claude/rules/skill-invariants.md`'s own provenance note) for `/bug` work, and archived/renamed sprint directories from prior cycles can also remain on disk. Any such directory with a `COMPLETED` marker now counts toward `completed_sprints`, but `total_sprints` never counts it. At `head/.claude/scripts/workflow-state.sh:148`, `[[ "${completed_sprints}" -ge "${total_sprints}" ]] && [[ "${total_sprints}" -gt 0 ]]` drives `STATE_COMPLETE` — e.g. with `sprint.md` declaring 2 numbered sprints, only `sprint-1` actually done, but a completed `sprint-bug-102` also present, `completed_sprints=2 >= total_sprints=2` fires `STATE_COMPLETE` even though `sprint-2` was never implemented. This causes `/loa` and the golden-path status logic to stop suggesting `/implement sprint-2` and report the project as finished prematurely.
  The old implementation (`base/.claude/scripts/workflow-state.sh:78-91`) avoided this by iterating `i=1..total` and checking `sprint-${i}/COMPLETED` directly, so only numbered sprints tracked in `sprint.md` could ever be counted — the fix should preserve that invariant (e.g. keep iterating by numeric ID, or filter the `find` results to `sprint-[0-9]+` and cap at `total_sprints`) rather than trusting every `sprint-*` directory on disk.

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/adapters/loa_cheval/providers/anthropic_adapter.py:74-223` — the entire `_is_billing_class_error` classification (and its `_BILLING_CLASS_TOKENS` table) is deleted, so a 4xx response that previously indicated an account-level condition (e.g. Anthropic's "credit balance too low" HTTP 400) now raises `InvalidInputError` instead of `ProviderUnavailableError`. Elsewhere in this same file, `status >= 500` and `status == 429` are still routed to `ProviderUnavailableError`/`RateLimitError` respectively (`head/.claude/adapters/loa_cheval/providers/anthropic_adapter.py:132-138`, `214-219`), which is presumably so the retry/failover layer treats them as transient/provider-side rather than terminal. Billing-class errors are also provider-side (not a caller mistake), so folding them into the terminal `InvalidInputError` bucket looks like a behavior loss rather than a pure simplification — if a downstream retry/failover layer keys off exception type (plausible, given the removed code went out of its way to route billing errors through `ProviderUnavailableError`), this silently stops failing over on billing exhaustion. No test file in this workspace references billing-class handling either way, so I can't confirm downstream impact from tests alone; the PR description ("plain 4xx handling") reads as an intentional simplification, but the rationale for dropping billing-class detection specifically isn't stated. Worth confirming against the SDD/retry layer before merging, since reverting is easy now but the failure mode (silent loss of billing-outage failover) is hard to notice later.
- **LOW** (confidence: medium) This PR bundles three functionally unrelated changes (a safety-hook regex rewrite, a provider adapter simplification, and a sprint-counting script change) under one commit/PR. Per the Karpathy "surgical changes" principle, consider splitting these into separate PRs — it would have made the multi-root find-exec regression and the sprint-counting decoupling easier to catch in isolated review, and makes revert/bisect harder if only one of the three needs to be reverted.

## Overall Assessment

Two of the three changes in this PR introduce concrete regressions: the `find -exec` root-capture change opens a real bypass of the destructive-rm safety net (CRITICAL), and the sprint-counting change can cause the workflow state machine to misreport a project as complete before all planned sprints are done (HIGH). Both are counted below. Requesting changes.
