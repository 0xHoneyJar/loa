# Review: chore(hooks,scripts): simplify carrier-value regexes, redaction patterns and sprint counting

Scope: three shell helpers touched — `.claude/hooks/safety/block-destructive-bash.sh`,
`.claude/scripts/lib/invoke-diagnostics.sh`, `.claude/scripts/workflow-state.sh`. No
sprint plan / beads / a2a artifacts exist for this review; assessed directly against
the diff and the surrounding code in `head/`.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:72` — `get_total_sprints` now prints two lines ("0\n0") whenever `sprint.md` exists but contains zero `^## Sprint [0-9]` headers, silently corrupting every numeric caller. `grep -c` prints the count (`0`) to stdout **and** exits status 1 when the count is zero (POSIX/GNU behavior: exit 1 means "no matches found," independent of `-c`). The new one-liner `grep -c ... 2>/dev/null || echo "0"` therefore executes *both* halves on a legitimate zero-match `sprint.md`: `grep` prints `0`, its exit code trips the `||`, and `echo "0"` prints a second `0`. The original code (`n=$(grep -c ... || true); echo "${n:-0}"`) avoided exactly this by capturing into a variable first, which is why it existed — this "simplification" reintroduces the classic `grep -c` pitfall the old code was written to dodge.
  Concrete failure: `get_completed_sprints()` (`head/.claude/scripts/workflow-state.sh:86-92`) does `total=$(get_total_sprints); for ((i = 1; i <= total; i++))` — with `total="0\n0"` the arithmetic context sees an embedded newline and errors out (or, under `set -e` callers, aborts the script). `determine_state()` (`head/.claude/scripts/workflow-state.sh:147,158`) does `seq 1 "${total_sprints}"` with the same multi-line value, which `seq` rejects as an invalid argument. This hits any project whose `sprint.md` exists before the first `## Sprint N` heading is written (a real transitional state, not a corner case) and breaks `/loa` status / workflow-state consumers.

- **HIGH** (confidence: medium) `head/.claude/scripts/lib/invoke-diagnostics.sh:50` — AWS key-ID redaction is narrowed from `(AKIA|ASIA|AROA|AGPA|AIPA|ANPA|ANVA)[A-Z0-9]{16}` to bare `AKIA[A-Z0-9]{16}`. This drops redaction for `ASIA*` (STS temporary/session credentials — arguably the most commonly leaked AWS credential type in CI/agent logs), `AROA*` (role IDs), `AGPA*`/`AIPA*`/`ANPA*`/`ANVA*` (group/instance-profile/other principal IDs). These are all real, publicly documented AWS identifier prefixes (the same set gitleaks/trufflehog scan for); an unredacted `ASIA...` in `.run`/diagnostic logs is a live temporary-credential leak, not a cosmetic difference. The PR description justifies this as "trimmed back to the documented AWS access-key shape," but no doc citation is given, and the effect is a functional security regression in a secret-redaction path with no compensating control.

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/scripts/lib/invoke-diagnostics.sh:48` — the Bearer-token pattern loses `=` from its character class (`[A-Za-z0-9=._-]+` → `[A-Za-z0-9._-]+`). Base64 bearer/JWT-style tokens commonly end in `=`/`==` padding; the trimmed class stops matching before the padding, so the sed replacement leaves the literal padding characters trailing the `***REDACTED***` marker (e.g. `Bearer ***REDACTED***==`) instead of consuming the whole token. The leaked bytes are only padding (not secret-bearing) so impact is low, but this change isn't mentioned anywhere in the PR description (which only calls out the AWS pattern), so it reads as an unreviewed, undisclosed narrowing of a redaction regex — the kind of change that deserves its own line in the description and, ideally, a golden-output test.

- **MEDIUM** (confidence: medium) `head/.claude/hooks/safety/block-destructive-bash.sh:210-236` — this deletes two independent hardenings from the git/br/gh "carrier value" exemption in `block-destructive-bash.sh` with zero rationale in the PR description and no comment/doc updates to match:
  1. The `'`/`"` exclusion in the prefix classes (`_bdb_re_git`/`_bdb_re_brbd`/`_bdb_re_gh`, base had `[^;&|'\"]*`, head has `[^;&|]*`) is gone. That exclusion was load-bearing enough to be called out by name in the adjacent "cycle-120 C-D3a" design-rationale block (`head/.claude/hooks/safety/block-destructive-bash.sh:203-208`, still present and unmodified) — the file's own comment already claimed the narrower `[^;&|]*` behavior before this PR (base code and base comment disagreed), which is itself a sign this exclusion was a deliberate, undocumented fix that a "restore the comment's shape" refactor just quietly reverted.
  2. The `_bdb_re_tail` regex and its `while` loop (base lines 214, 236-248) are removed outright. That loop was what let `_bdb_scrub` redact a *second and subsequent* `-m`/`--message`/`-d`/`--description`/`--body`/`--title` value in the same carrier match (git allows repeated `-m` for multi-paragraph commits; `gh pr create` allows one `--title` and one `--body` but bd/br flows can repeat `-d`). After this change only the first value in a carrier match is ever scrubbed; every later quoted value in the same statement is left as plain text and re-enters the normal destructive-pattern scan.
  Concrete failure scenario: `git commit -m "add feature" -m "note: this replaces the old DROP TABLE migration"` — the second `-m` body text (ordinary prose describing what the commit does, not executable) is no longer treated as an inert carrier value. It stays in `_cmd_match` and match against P8 (`DROP ... TABLE`) fires, and the commit is **blocked** with `BLOCKED [FR-1.4]`, even though nothing destructive is being executed. This is a functional regression against the fence's own stated purpose (avoid false-positives on inert commit-message content) rather than a bypass, but it lands in a file whose header explicitly requires "fail-open… must never fail closed" posture and whose every other line carries an adversarial-review citation (cycle numbers, bug IDs, cross-model dissent notes) — this diff carries none, for changes to the same regex family. Recommend restoring the tail loop (or covering the multi-value case with an equivalent test) and re-adding the quote exclusion, or explicitly re-justifying its removal with a test that proves no case in the anti-spoof / carrier-scrub design breaks.

- **LOW** (confidence: high) `head/.claude/scripts/workflow-state.sh:72` (secondary note) — even setting aside the double-echo bug above, `2>/dev/null` swallows only stderr; a `grep` failure for reasons other than "no match" (e.g., permission denied) still exits non-zero and falls into the same `|| echo "0"` path, which is intentional/acceptable per the existing fail-safe pattern — noted only for completeness, not blocking.

## Summary

Two of the three files in this "chore: simplify" PR touch security-relevant paths (destructive-command fencing and secret redaction) and both weaken redaction/blocking coverage in ways the PR description does not fully disclose or justify; the third (`workflow-state.sh`) reintroduces a concrete `grep -c` correctness bug that the code being "restored" was originally written to avoid. None of the three files gained or updated tests alongside the behavior change. Requesting changes on the AWS-key-prefix regression and the `get_total_sprints` double-echo bug as blocking; the Bearer regex and carrier-regex/tail-loop removals should at minimum be explained and covered by a regression test before merge.
