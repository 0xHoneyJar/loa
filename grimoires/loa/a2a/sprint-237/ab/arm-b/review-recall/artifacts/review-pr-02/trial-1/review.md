# Review: refactor(audit,spiral,semver): drop strict-verify plumbing, backtick masking and prerelease branches

## Overall Assessment

This PR touches three System Zone scripts and removes three independent pieces of previously-hardened logic under a "simplification" banner. Two of the three removals are low-risk, consistent simplifications that match the PR description. The third — stripping the merge-gate strict-verification path out of `audit_envelope.py` — removes defenses that the codebase's own comments identify as responses to named attack scenarios (`ATK-3`, `ATK-4`) and a prior security review (issue #690, "Bridgebuilder F4 hardening"), with no accompanying justification for why those attacks are no longer a concern. That is a security regression, not a cleanup, and blocks approval on its own.

A related, lower-severity regression: removing the backtick-masking step in `spiral-evidence.sh` reintroduces the exact false-positive class that bug `#1175` was fixed to prevent, for the "bare path" matching branch.

## Changes Required

- **CRITICAL** (confidence: medium) `head/.claude/adapters/loa_cheval/audit_envelope.py:462` — `_check_trust_store()` now unconditionally treats `BOOTSTRAP-PENDING` as passing (`head/.claude/adapters/loa_cheval/audit_envelope.py:468`, `if status in ("BOOTSTRAP-PENDING", "VERIFIED"): return`), and `audit_verify_chain()` (`head/.claude/adapters/loa_cheval/audit_envelope.py:508`) no longer accepts `verify_for_merge`. The removed code (`base/.claude/adapters/loa_cheval/audit_envelope.py:469-487`) existed specifically to make a merge-gate caller *refuse* an unsigned trust-store rather than silently proceed, per its own error message: `"[TRUST-STORE-BOOTSTRAP-PENDING] ... strict audit verification refuses BOOTSTRAP-PENDING (ATK-3)"`. `_strict_verify_enabled()` (deleted, was `base/.claude/adapters/loa_cheval/audit_envelope.py:136-138`) was also driven by the `LOA_AUDIT_STRICT_VERIFY` env var, independent of any caller passing a keyword argument — any external invocation (e.g. a merge-pipeline script such as `post-merge-orchestrator.sh`, referenced in `CLAUDE.loa.md`'s Merge Constraints section, which this diff does not touch) that sets that env var to request strict verification will now have that request silently ignored rather than erroring. Concrete failure: an attacker (or a broken bootstrap) leaves the trust-store unsigned or replaces it with an empty/`BOOTSTRAP-PENDING` document at merge time; before this change, a merge-gate caller requesting strict verification would refuse the merge; after this change there is no way to request that refusal at all — every caller, forever, gets the permissive behavior. This directly undoes the ATK-3/ATK-4 hardening and issue #690 remediation without any stated threat-model change.
- **HIGH** (confidence: medium) `head/.claude/adapters/loa_cheval/audit_envelope.py:136` — `_resolve_pubkey_pem()` lost its `allow_local_fallback` parameter, so a `.pub` file dropped in the local key directory is now *always* accepted as a valid signer for a chain entry, even in a hypothetical strict/merge-gate call path. Combined with the `_check_trust_store` change above, this removes the second half of the same defense: even if a future caller wanted "trust only the signed trust-store, never a local file" semantics for a merge-time verification, that option no longer exists in the API.
- **MEDIUM** (confidence: medium) `head/.claude/scripts/spiral-evidence.sh:700` — Pattern 2 ("bare paths rooted at well-known top-level repo prefixes") now scans raw `$content` instead of the backtick-stripped `$content_bare` that existed in `base/.claude/scripts/spiral-evidence.sh:673-674, 702`. The adjacent, untouched comment block for Pattern 1 (`head/.claude/scripts/spiral-evidence.sh:681-690`) documents exactly why this masking mattered: "backtick prose also wraps shell commands (`` `bash tools/x.sh` ``, `` `yq -o=json ... file.yaml` ``) and CLI flags ... that contain `/`+extension and matched as deliverable paths, failing cycles with `IMPL_EVIDENCE_MISSING`" (bug `#1175`). Pattern 1 guards against this for its own match by filtering out anything containing whitespace, but Pattern 2 has no such guard — it greedily matches any `src|tests|.claude/scripts|.claude/hooks|grimoires/...` substring anywhere in the text, including inside a backtick-quoted shell command example. Concrete failure: a sprint.md deliverables section containing prose like `` `bash tools/deploy.sh --config grimoires/loa/deploy.yaml` `` will now have `grimoires/loa/deploy.yaml` extracted by Pattern 2 as a declared deliverable, reintroducing the same `IMPL_EVIDENCE_MISSING` false-positive class `#1175` was opened to fix.

## Observations

- `head/.claude/scripts/semver-bump.sh:55-78` (`get_version_from_tag`) and `:80-92` (`bump_version`) — dropping prerelease (`alpha`/`beta`/`rc`) tag parsing is consistent with the PR title/description and is not silently unsafe: `get_version_from_tag` no longer filters tags with a strict grep, but `bump_version`'s own format validation (`^[0-9]+\.[0-9]+\.[0-9]+$`) still rejects anything that isn't a plain release version, so a stray non-conforming tag fails loudly rather than corrupting a bump. Low severity, no action required unless prerelease tagging is still in use elsewhere in the release pipeline (not visible in this diff).
- `head/.claude/scripts/semver-bump.sh:74` — two added one-line comments (`# Get current version...`, `# Bump a version string...`) are harmless but marginal; the function names already say this.

## Documentation / Justification Gap

None of the three changes reference a design doc, ADR, or security sign-off for removing the ATK-3/ATK-4 hardening or the `#1175` false-positive guard on the bare-path branch. Given this repo's own review protocol treats named attack IDs and numbered bug fixes as durable institutional memory (comments throughout `audit_envelope.py` and `spiral-evidence.sh` cite issue/attack numbers precisely so future changes don't quietly re-open them), this PR should not land without either (a) restoring the strict-verify path and the Pattern-2 backtick mask, or (b) an explicit, reviewed rationale for why ATK-3/ATK-4 and `#1175` no longer apply.
