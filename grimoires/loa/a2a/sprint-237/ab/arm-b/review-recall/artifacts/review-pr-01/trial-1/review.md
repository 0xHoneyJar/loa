## Overall Assessment

This PR is framed as a pure simplification/cleanup of three shell helpers, but two of the three
changes are functional regressions rather than neutral simplifications: the sprint-count "one-liner"
reintroduces a classic `grep -c` double-output bug that can crash `workflow-state.sh` state detection
under `set -e`, and the AWS-key redaction pattern drops coverage for `ASIA*` temporary/STS access key
IDs — a live-credential leak, not just a cosmetic trim. The destructive-bash regex simplification is
lower risk (the content-gate that actually blocks command-substitution danger is untouched) but does
quietly drop multi-flag carrier support without updating the extensive surrounding commentary that
describes this fence's behavior.

## Changes Required

- **CRITICAL** (confidence: high) `head/.claude/scripts/workflow-state.sh:72` — `grep -c "^## Sprint [0-9]" "${SPRINT_FILE}" 2>/dev/null || echo "0"` double-prints when `${SPRINT_FILE}` exists but contains **zero** matching `## Sprint N` headings: `grep -c` always writes its count (`0`) to stdout even with no matches, but exits `1` in that case, so bash *also* runs `echo "0"` — the function returns `"0\n0"` instead of `"0"`. The previous code (base `workflow-state.sh:78-81`, `n=$(grep -c ... || true); echo "${n:-0}"`) captured grep's output first and only used `${n:-0}` for the genuinely-empty-stdout case, so it always emitted exactly one line. With this "restored one-liner," any caller that does `total_sprints=$(get_total_sprints)` while `sprint.md` exists without any sprint headers yet (e.g. a freshly scaffolded sprint plan) gets `total_sprints="0\n0"`. `get_completed_sprints()` (`head/.claude/scripts/workflow-state.sh:88`) then runs `for ((i = 1; i <= total; i++))` with that multi-line value, which is a bash arithmetic syntax error — fatal under this file's `set -euo pipefail` (`head/.claude/scripts/workflow-state.sh:16`). `determine_state()`'s `[[ "${completed_sprints}" -ge "${total_sprints}" ]]` (`head/.claude/scripts/workflow-state.sh:151`) hits the same corrupted value. This breaks the Golden Path status/state detection (`/loa`, `/run-status`) precisely in the zero-sprints edge case the guard was written to handle.

- **HIGH** (confidence: high) `head/.claude/scripts/lib/invoke-diagnostics.sh:50` — the AWS access-key redaction was narrowed from `(AKIA|ASIA|AROA|AGPA|AIPA|ANPA|ANVA)[A-Z0-9]{16}` to `AKIA[A-Z0-9]{16}` only. The PR description calls this "trimmed back to the documented AWS access-key shape," but AWS issues **two** access-key-ID prefixes that function as real bearer credentials when paired with a secret key: `AKIA` (long-term IAM user keys) and `ASIA` (temporary/STS credentials — the prefix used by assumed roles, EC2/ECS/Lambda instance credentials, and OIDC-federated CI sessions, i.e. the most common shape in modern pipelines). Dropping `ASIA` means `redact_secrets()` will no longer scrub a live temporary AWS access key ID out of diagnostic logs written by `setup_invoke_log`/`log_invoke_failure`, i.e. exactly the secret-redaction path this file exists for. (The other dropped prefixes — `AROA`/`AGPA`/`AIPA`/`ANPA`/`ANVA` — are internal AWS resource identifiers, not credential material, so removing those is fine; `ASIA` should be restored alongside `AKIA`.)

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/hooks/safety/block-destructive-bash.sh:210-212` — removing the quote-exclusion from the carrier prefix classes (`[^;&|'\"]*` → `[^;&|]*`) plus deleting the `_bdb_re_tail` follow-up loop (base `.claude/hooks/safety/block-destructive-bash.sh:214,236-248`) changes which value gets redacted in a multi-flag command. Because bash `[[ =~ ]]` uses POSIX leftmost-longest matching, a command like `git commit -m "first" -m "second"` now matches through the first quoted value in the (now quote-permissive) prefix and only the *last* `-m` value is content-gated and blanked; the first value is left verbatim in `_cmd_match`. This isn't a bypass — the `$(`/backtick command-substitution gate that guards against real danger is unchanged and still sees everything not consumed as the trailing value — but it does mean legitimate multi-`-m`/`-d`/`--body` commits/PRs whose *earlier* message contains destructive-looking text (e.g. `git commit -m "note: don't rm -rf here" -m "final message"`) can now trip a false-positive block that the removed tail loop was specifically added to prevent. The surrounding header comments (lines 203-213) weren't updated to note this narrowed carrier-matching behavior.
- **LOW** (confidence: medium) `head/.claude/scripts/lib/invoke-diagnostics.sh:48` — the Bearer-token pattern dropped `=` from `[A-Za-z0-9=._-]+` to `[A-Za-z0-9._-]+`. This only affects trailing base64 `=` padding (never mid-token), so at most a harmless `==` remnant survives redaction (e.g. `Bearer ***REDACTED***==`) — no actual secret bytes leak, but it's an unexplained narrowing with no corresponding comment update.
