# Review: refactor(audit,spiral,semver): drop strict-verify plumbing, backtick masking and prerelease branches

## Overall Assessment

The PR description frames this as pure simplification ("single code path again"), but two of the three touched files lose real behavior that the surrounding code and comments identify as security- or correctness-critical, and the third drops a documented false-positive guard. None of these are refactor-neutral. This is CHANGES_REQUIRED.

## Changes Required

- **CRITICAL** (confidence: high) `head/.claude/adapters/loa_cheval/audit_envelope.py:462-473` — `_check_trust_store()` now unconditionally treats `BOOTSTRAP-PENDING` as pass-through, and the `strict_verify` parameter (previously threaded from `audit_verify_chain(..., verify_for_merge=True)` and from the `LOA_AUDIT_STRICT_VERIFY` env var) is gone entirely. Before this diff, `audit_verify_chain` had exactly one caller-facing lever for merge-time strictness — comments tagged it against named attack scenarios: `[TRUST-STORE-BOOTSTRAP-PENDING] ... strict audit verification refuses BOOTSTRAP-PENDING (ATK-3)` (base/.claude/adapters/loa_cheval/audit_envelope.py:48-52) and `[TRUST-STORE-MISSING] strict audit verification requires a readable trust-store (ATK-4)` (base:68-72). Any external caller that still exports `LOA_AUDIT_STRICT_VERIFY=1` (e.g. a CI/merge-gate wrapper around `audit_verify_chain`, per the repo's own "post-merge-orchestrator" and "NEVER skip quality gates" conventions) will now get silently non-strict verification — no error, no warning, just a trust-store that was deleted or never bootstrapped passing chain verification as if it were legitimate. Same root cause removes the `allow_local_fallback` guard in `_resolve_pubkey_pem` (`head/.claude/adapters/loa_cheval/audit_envelope.py:136-160`, base equivalent at base:13-29) and the strict-mode raise in `_read_trust_cutoff` (`head/.claude/adapters/loa_cheval/audit_envelope.py:476-494`, base:59-84) — both previously refused permissive fallbacks under `strict_verify`, both now always take the permissive path. Nothing in the PR description explains why ATK-3/ATK-4 no longer apply; if the merge-gate caller was actually deleted, that removal isn't shown in this diff, so the mitigation is dropped without evidence the threat it defended against is gone. Failure scenario: an attacker (or a broken bootstrap) deletes/never-creates the trust-store; a merge pipeline that previously ran `LOA_AUDIT_STRICT_VERIFY=1 audit_verify_chain(log_path)` and refused to merge on `[TRUST-STORE-BOOTSTRAP-PENDING]`/`[TRUST-STORE-MISSING]` now merges cleanly because both raises are gone and the env var is never read.

- **HIGH** (confidence: high) `head/.claude/scripts/spiral-evidence.sh:700` — Pattern 2 now scans raw `$content` instead of the backtick-stripped `$content_bare` that was computed and used here in the base version (`base/.claude/scripts/spiral-evidence.sh:673-674,702`). Pattern 1 (line 679) already relies on backticks being present to recognize a "declared deliverable" and explicitly filters out command-example false positives — whitespace, globs, and `-`/`@`-prefixed CLI flags (comment at head:683-689, citing issue #1175: "backtick prose also wraps shell commands ... and CLI flags ... that contain `/`+extension and matched as deliverable paths, failing cycles with IMPL_EVIDENCE_MISSING"). Pattern 2 has no equivalent guard — it only avoided this class of false positive because `content_bare` had already deleted every backtick-delimited span before Pattern 2 ran. With that stripping removed, any bare top-level path (`src/…`, `tests/…`, `.claude/scripts/…`, `.claude/hooks/…`, `grimoires/…`) mentioned inside a backtick-wrapped prose example — e.g. `` `run .claude/scripts/spiral-evidence.sh --check src/foo.ts to validate` `` in a sprint.md "Risks" or "Technical Tasks" note — is now extracted by Pattern 2 as if it were a declared deliverable, because Pattern 2's boundary check only requires a non-path-char (a space qualifies) before the prefix, not backtick-awareness. This reintroduces exactly the failure mode #1175 was opened to fix, just via the unguarded pattern instead of the guarded one: a legitimate sprint can now fail with a spurious `IMPL_EVIDENCE_MISSING` for a path that was only ever mentioned as a command-example, not declared as a deliverable.

- **HIGH** (confidence: medium) `head/.claude/scripts/semver-bump.sh:57` — `get_version_from_tag` dropped both the second glob (`'v[0-9]*.[0-9]*.[0-9]*-*'`) and, more importantly, the trailing `grep -E '^v[0-9]+\.[0-9]+\.[0-9]+(-(alpha|beta|rc)\.[0-9]+)?$'` validation that the base version used to constrain the selected tag to a real semver (release or prerelease) shape. The remaining git glob `v[0-9]*.[0-9]*.[0-9]*` still matches prerelease-suffixed tags (git's glob `*` matches any characters, including a `-rc.1` suffix after the final numeric segment), so a repo whose most recent tag is a prerelease (e.g. `v1.4.0-beta.2`) still has that tag selected as `current` by `--sort=-v:refname | head -1`. That string is then passed into `bump_version` (semver-bump.sh:333), which — per this same PR's other change at semver-bump.sh:83 — now hard-rejects anything not matching `^[0-9]+\.[0-9]+\.[0-9]+$` and returns 1. Under `set -euo pipefail` (semver-bump.sh:19) this aborts the whole script instead of computing a bump. The base version handled this input correctly via `prerelease_re`, incrementing the prerelease counter. The PR's stated intent ("returns semver-bump.sh to release-only version parsing") isn't matched by a corresponding change to tag selection to skip/exclude prerelease tags — the two halves of the "single code path" are now inconsistent: one still admits prerelease tags, the other now refuses them outright. Any repo with an as-yet-unreleased prerelease tag as its latest tag will have version-bump automation (which CLAUDE.loa.md's Merge Constraints require routing through this exact script) fail hard.

None beyond the above — the removed docstring text ("test/CI fallback, refused in strict verify" → "test/CI fallback") and comment cleanups are consistent with the (incorrect) premise that strict mode no longer exists, but carry no independent risk beyond the CRITICAL finding above.
