# Review: refactor(hooks,cheval,state): single-token find roots, plain 4xx handling, historical sprint counting

## Changes Required

- **CRITICAL** (confidence: high) `head/.claude/hooks/safety/block-destructive-bash.sh:776` — the new `_re_find_exec_prefix` regex captures only `find`'s *first* path token as group 3 (`([^;&|)[:space:]]+)`), and the removed token-walking loop (previously at base/.claude/hooks/safety/block-destructive-bash.sh:806-814, deleted) no longer verifies that this is the *only* root before treating it as authoritative. `find` accepts multiple starting paths (`find root1 root2 -exec ...`), and the old code explicitly zeroed `_seg_find_root` whenever more than one root token was present (`[[ "$_find_root_count" -ne 1 ]] && _seg_find_root=""`), forcing multi-root invocations through the conservative generic per-arg ladder. That safeguard is gone. Concretely: `find /tmp/safe /etc -maxdepth 1 -exec rm -rf {} \;` — `head/.claude/hooks/safety/block-destructive-bash.sh:807` sets `_seg_find_root="/tmp/safe"` (the first token only, silently dropping `/etc`); since the rm segment's own args are placeholder-only (`{}`), execution falls into the placeholder-classification branch at `head/.claude/hooks/safety/block-destructive-bash.sh:850-878`, where `/tmp/safe` matches `_re_allow_list`'s `/tmp/.+` at `head/.claude/hooks/safety/block-destructive-bash.sh:765` and the segment is silently **allowed** (`: # explicit safe relative root`) — even though the same `find` invocation will also recursively `rm -rf` everything under `/etc`. This is a destructive-command-blocking security hook; a smuggled second root bypasses it entirely for a genuinely catastrophic delete. The new inline comment at `head/.claude/hooks/safety/block-destructive-bash.sh:773-775` documents that flags-before-root is an accepted gap, but does not address (or appear to have considered) this multi-root bypass, which is a regression from the prior behavior, not a pre-existing gap.

- **HIGH** (confidence: medium) `head/.claude/scripts/workflow-state.sh:83` — `get_completed_sprints` now enumerates every directory matching the glob `sprint-*` under `a2a/` via `find ... -name "sprint-*"` and counts any with a `COMPLETED` marker, rather than checking `sprint-1..sprint-${total}` as before (base/.claude/scripts/workflow-state.sh:78-85, using `get_total_sprints`-bounded indices). The glob also matches non-plan directories such as bug-fix sprints (`sprint-bug-102`-style names, referenced as a real naming convention in `.claude/loa/CLAUDE.loa.md`'s NEVER-rules table) and any sprint directories left over from a prior/longer cycle. Concrete failure: `sprint.md` currently declares 2 sprints (`get_total_sprints` → 2), `a2a/sprint-1/COMPLETED` exists, `sprint-2` has not started, but `a2a/sprint-bug-102/COMPLETED` exists from an earlier bug fix — `get_completed_sprints` now returns 2 (counting `sprint-1` and `sprint-bug-102`), and the caller at `head/.claude/scripts/workflow-state.sh:148` (`completed_sprints -ge total_sprints`) incorrectly reports `STATE_COMPLETE` even though the real `sprint-2` was never implemented. The same comparison is repeated at `head/.claude/scripts/workflow-state.sh:366-367`. The fix for cross-cycle/historical numbering needs to filter to numeric `sprint-N` names bounded by (or reconciled against) `get_total_sprints`, not an unbounded glob.
