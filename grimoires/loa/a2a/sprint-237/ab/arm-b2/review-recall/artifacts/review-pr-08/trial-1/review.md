# Review: chore(ledger,tools,cheval): lighter ledger content check, simpler heredoc skipping, fewer except clauses

## Overall Assessment

All three "simplifications" in this PR remove logic that was specifically added to guard against a named, previously-fixed failure mode, and each removal reopens a variant of that same failure mode rather than genuinely simplifying dead weight. None of the three changes are accompanied by a test that would have caught the regression. Changes required before merge.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:157` — The content guard was weakened from "valid JSON **and** a single top-level object" (`jq -es 'length == 1 and (.[0] | type == "object")'`, base/.claude/scripts/ledger-lib.sh:153) to "any valid JSON" (`jq empty`). A `content` value of the literal string `null` now passes this check, and then at `head/.claude/scripts/ledger-lib.sh:179` `jq --arg ts ... '.last_updated = $ts'` auto-vivifies `null` into `{"last_updated": "<ts>"}` — jq treats `null | .x = v` as `{} | .x = v`, so the assignment does **not** fail and `updated_content` is non-empty. The result is silently written over the real ledger via the atomic-write path (lines 187-204), discarding `cycles`, `active_cycle`, and `next_sprint_number`. This is exactly the class of bug the guard's own comment describes (bug 20260808-a008c6: "passed through the last_updated jq stamp … and truncated the ledger"), just triggered by `null` instead of empty string. Verified directly: `echo null | jq '.last_updated = "x"'` → `{"last_updated": "x"}` (non-array/non-null JSON like `"str"` or `[]` does correctly error out of `.last_updated = $ts` and get caught by the `-z "$updated_content"` check at line 180, so the hole is specific to `null`). No current caller in this file constructs `ledger_content` as literal `null`, so this is latent rather than actively triggered today — but the type check existed precisely to make this class of bug structurally impossible regardless of caller behavior, and this change removes that invariant for no stated benefit (the PR description calls it "lighter," not "fixes a false positive").

- **HIGH** (confidence: high) `head/tools/check-no-swallowed-jq.sh:138-146` — The heredoc-body skip logic dropped the `hd_exec` distinction entirely (removed `_hd_command`, `INTERP` table, and the quoted/piped-to-interpreter check that lived in `base/tools/check-no-swallowed-jq.sh:158-163`). Previously, only heredocs that were *not* going to execute as shell/interpreter code (a quoted delimiter assigned to a variable, e.g. `cat <<'EOF'` capturing fixture/doc text) were skipped from scanning; heredocs piped into `bash`/`sh`/`python`/etc. (`hd_exec=1`) still had their body lines checked for the swallowed-jq shape. The new code at lines 138-146 skips **every** heredoc body unconditionally, with no distinction between fixture text and executable script content. Concretely: a gate-critical script (one of `ENFORCED_FILES` or `red-team-*`) that assembles an inline script via `bash <<EOF\n...\njq -r '.verdict' file.json || echo "clean"\n...\nEOF` will no longer be flagged — the exact `jq ... || echo <default>` shape this scanner exists to catch (KF-004/KF-015, per the file's own header comment) now has a heredoc-shaped blind spot on the very files it is scoped to protect. The new "Step 1" comment at line 135-137 ("skip fixture/documentation text … Without this, --root scans of bats tests can flag planted bad examples") describes the old, narrower rationale but the code beneath it no longer implements that narrower rule — comment and behavior have diverged.

- **HIGH** (confidence: high) `head/.claude/adapters/loa_cheval/providers/agy_headless_adapter.py:156` — The `except ValueError` handler between the `FileNotFoundError` and `OSError` clauses was deleted. `subprocess`-family calls raise a bare `ValueError` (not an `OSError` subclass) for un-execable argv such as a prompt string containing an embedded NUL byte — the exact scenario the deleted handler's message named ("agy -p got un-execable argv (embedded NUL in the prompt?)"). With the handler gone, that `ValueError` is no longer caught by the sibling `except OSError as exc:` at line 157 (ValueError does not inherit from OSError) and is not caught by the outer `except _SemaphoreExhausted` at line 166 either, so it propagates out of `complete()` as a raw, unconverted exception instead of a `ProviderUnavailableError`. Every neighboring handler in this same block exists specifically to turn a low-level exec failure into a `ProviderUnavailableError` so "the fallback chain advances" (per the comments at lines 126-127 and 159-160); removing this one handler means an embedded-NUL prompt crashes the whole cheval invocation instead of walking to the next provider in the chain, which is the opposite of every other error path in this function.

## Observations

- `head/.claude/scripts/ledger-lib.sh:157,179` — `printf '%s' "$content"` was replaced with `echo "$content"` in both spots. In this specific file it's consistent with existing `echo "$ledger_json" > "$ledger_path"` usage elsewhere (e.g. `init_ledger`), and JSON text always starts with `{`/`[`/a digit/`"`/`true`/`false`/`null` so the "leading `-e`/`-n` swallowed as an echo flag" hazard doesn't apply here. Low risk, but `printf '%s'` remains the more portable choice if this code is ever run under `sh`/POSIX mode rather than bash, since POSIX `echo` may interpret backslash escapes inside JSON string values (e.g. literal `\n` sequences) that bash's non-POSIX `echo` builtin does not.
