# Review: refactor(hooks,cheval,state): single-token find roots, plain 4xx handling, historical sprint counting

Three unrelated changes bundled in one PR: a regex simplification in the destructive-bash safety
hook, removal of billing-class 4xx classification in the Anthropic adapter, and a rewrite of
`get_completed_sprints` in `workflow-state.sh`. Reviewed each independently.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:79-88` — `get_completed_sprints` now scans every `${a2a_dir}/sprint-*` directory on disk and counts any with a `COMPLETED` marker, decoupled from `get_total_sprints` (`workflow-state.sh:70-76`, which only counts `## Sprint N` headings in the *current* `sprint.md`). The one caller that matters, `determine_state`'s "all sprints complete?" check at `head/.claude/scripts/workflow-state.sh:148`, does `[[ "${completed_sprints}" -ge "${total_sprints}" ]]`. Concrete failure: current `sprint.md` defines Sprint 1 and Sprint 2 (`total_sprints=2`); Sprint 1 is complete, Sprint 2 is still in progress; but an unrelated `a2a/sprint-bug-107/COMPLETED` (or a leftover `a2a/sprint-3/COMPLETED` from a prior cycle whose directory wasn't cleaned up) exists on disk. `get_completed_sprints` now returns 2 (sprint-1 + the unrelated directory), which is `-ge 2`, so `determine_state` reports `STATE_COMPLETE` even though Sprint 2 hasn't been reviewed or audited. This flows into `/loa`'s suggested-command output and progress percentage (lines 366-367), and could steer a user toward `/ship`/`/archive-cycle` while a sprint is still open. The base version bounded the loop to `i=1..total` (`base/.claude/scripts/workflow-state.sh:80-86`), which structurally could never exceed `total_sprints`; the new version removes that bound without adjusting `get_total_sprints` to match, breaking the invariant the comparison on line 148 depends on. The PR's stated goal ("historical sprint counting", i.e. picking up non-numeric dirs like `sprint-bug-*`) is reasonable, but the fix needs to either (a) filter the directory scan to only sprint IDs that exist in the current plan, or (b) make `get_total_sprints` count the same universe `get_completed_sprints` now scans.

## Observations

- `head/.claude/hooks/safety/block-destructive-bash.sh:776,807` — the new `_re_find_exec_prefix` capture (`([^;&|)[:space:]]+)`) grabs only `find`'s first whitespace-delimited token as `_seg_find_root`, replacing the old token-walk that verified exactly one root operand preceded any flag. For a multi-root invocation like `find /etc ./safe-dir -exec rm -rf {} \;`, the new code validates only `/etc` (correctly hits the BLOCK list) and never even looks at `./safe-dir`, which happens to be harmless here — but the inverse ordering, `find ./safe-dir /etc -exec rm -rf {} \;`, produces `_seg_find_root="./safe-dir"`, matches the ALLOW list, and the segment is treated as an allowed find-exec regardless of the real second root `/etc`. I traced the base version for the same input: its token loop increments `_find_root_count` past 1 for any second non-flag token and resets `_seg_find_root=""` before the ladder runs, which sends the segment through the plain rm-args ladder instead — for a placeholder-only rm invocation (`{}`/`\;`/`+`), that ladder also finds nothing dangerous and silently allows it, so base has the same net permissiveness for this exact shape. Confidence is medium only because I could not find a regression test fixture in this diff (no test files were touched) exercising multi-root `find` invocations either before or after, so I can't confirm the fixture suite pins this behavior either way — flagging as non-blocking since it doesn't appear to be a new hole introduced by this PR, but it deserves a fixture given the hook explicitly documents the single-token scope change and calls out the flags-before-root gap without mentioning the multi-root gap at all.
- `head/.claude/adapters/loa_cheval/providers/anthropic_adapter.py:139,171,219,223` — removing `_is_billing_class_error` (and its two call sites) means every Anthropic 4xx, including account-side conditions like `payment_required`/`insufficient_quota`/`credit_balance` that the deleted docstring (`base/.claude/adapters/loa_cheval/providers/anthropic_adapter.py:59-67`) explicitly called out as needing to "chain-walk via ProviderUnavailableError", now raises `InvalidInputError` instead. If `loa_cheval`'s provider-chain fallback logic treats `ProviderUnavailableError` as retryable/failover-eligible and `InvalidInputError` as terminal (the naming and the removed docstring both strongly imply this), then an Anthropic account running out of credits would now surface as a terminal "invalid input" to the caller instead of failing over to the next configured provider. This file alone doesn't show the dispatcher/chain code, so I can't confirm the downstream consequence, but the change silently reverses a deliberately-documented classification without touching the caller side or explaining the reversal in the PR description — worth a sentence in the PR body on why the billing-class carve-out is being dropped (was it producing false positives, or is this a genuine feature reversion?).
- No tests were touched by this PR for any of the three files, despite two of the three (the destructive-bash hook and the Anthropic 4xx classification) being security/reliability-sensitive regex and error-handling logic. Not blocking on its own since the eval harness only surfaces touched files, but worth confirming the existing bats/pytest suites (if any) still assert the removed/changed behavior rather than silently losing coverage.
