# Review: chore(ledger,tools,cheval): lighter ledger content check, simpler heredoc skipping, fewer except clauses

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:157` — The content guard was weakened from `jq -es 'length == 1 and (.[0] | type == "object")'` (slurp + single-object check) to a bare `jq empty`, which only validates that the input parses as JSON — it no longer rejects multiple concatenated JSON documents. `jq empty` exits 0 on input like `{"a":1}\n{"b":2}`, and the subsequent stamping step (`jq --arg ts ... '.last_updated = $ts'` at `head/.claude/scripts/ledger-lib.sh:179`) then applies the filter to *each* top-level value, producing two stamped JSON objects concatenated in `updated_content`. That non-empty, multi-document blob passes the `-z` check at line 180 and gets written atomically to the ledger file, silently corrupting it (single-JSON-object ledger becomes two documents) instead of the loud one-line stderr error the old check used to force. Verified locally: `jq '.last_updated="X"' ` on a two-document input emits two separate JSON objects rather than erroring. This defeats the exact class of "caller thinks it succeeded, ledger is corrupted" bug the surrounding comment (bug 20260808-a008c6) says this guard exists to prevent.

- **HIGH** (confidence: medium) `head/tools/check-no-swallowed-jq.sh:138-146` — The heredoc-skipping rewrite drops the old `hd_exec` classification that distinguished heredocs fed to an interpreter (`bash <<EOF`, `python3 <<EOF`, `... | sh`, an unquoted delimiter, etc.) from inert documentation heredocs (`cat <<'EOF'`). The old code only skipped scanning for the *inert* case and kept scanning inside *executable* heredocs, since a `jq ... || echo default` shape inside a `bash <<EOF ... EOF` block is real, run at execution time. The new code unconditionally skips every heredoc body regardless of whether it's fed to an interpreter. That means a gate-critical script (or anything under a future `--root` scan) containing e.g. `bash <<EOF\n... | jq -e '...' || echo '{}'\nEOF` would no longer be flagged by this tripwire, even though the swallowed-jq shape inside it is genuinely executed — exactly the KF-004/KF-015 "silent-clean gate" failure mode this scanner's own header (`head/tools/check-no-swallowed-jq.sh:5-11`) says it exists to catch. None of the current `ENFORCED_FILES` happen to use heredocs today, but the `--root` mode (used for the bats contract tests and the #1025 sweep, per the file's own usage comment) scans arbitrary trees where this pattern is plausible, and the change silently narrows detection coverage for a security-motivated scanner without a corresponding doc/scope-comment update (the "Tripwire scope" caveat at lines 38-43 was not updated to mention this new blind spot).

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/scripts/ledger-lib.sh:157` and `head/.claude/scripts/ledger-lib.sh:179` — `printf '%s' "$content"` was replaced with `echo "$content"` in both the guard and the stamping pipeline. Under bash this is low-risk in practice since ledger content always begins with `{`, but it's a step away from the safer, POSIX-portable idiom (`echo` can still special-case leading `-e`/`-n`/`-E` and its behavior varies across `xpg_echo`/POSIX-mode shells), and the project's own `.claude/rules/shell-conventions.md` "JSON Construction Safety" example uses `echo "$content" | jq empty` as the canonical idiom, so this isn't inconsistent with house style — flagging only because it's a needless behavior change bundled into a "content check" commit.

- **LOW** (confidence: low) `head/.claude/adapters/loa_cheval/providers/agy_headless_adapter.py:157-165` — Removing the `except ValueError` handler (which used to convert a NUL-byte-in-argv exec failure into `ProviderUnavailableError` so the multi-model fallback chain could advance) means that specific failure now propagates as a raw, uncaught `ValueError` instead of a handled provider error. This is the same "never crash the chain, always hand off to the next provider" contract the adjacent `OSError` handler at line 157 explicitly documents preserving. I could not find the call site that invokes this adapter in the provided diff (only touched files are included), so I can't confirm whether an outer layer coincidentally catches bare `ValueError` and still advances the chain — filing as an observation rather than a blocking finding pending that context, but the removal looks like a real regression against the documented "walk the chain, never crash" invariant.

## Overall Assessment

Two of the three changes in this "simplification" chore trade correctness for brevity in ways that reintroduce the exact bug classes their surrounding comments say they guard against: the ledger content check now accepts multi-document JSON that corrupts the ledger on write, and the heredoc-skipping rewrite blinds the swallowed-jq tripwire to executable heredocs. Both are cited by the code's own docstrings/comments as the reason the more careful (now-removed) logic existed. Recommend restoring the `-es`/single-object ledger guard (or an equivalent check that still rejects multi-document input) and restoring `hd_exec`-style discrimination between executable and inert heredocs before landing this PR.
