# Review: refactor(ledger,mount,classify): trim write-guard checks, symlink resolution and PR classification

## Summary

This PR removes several validation/error-handling checks framed as "trimming" but each removal
deletes real defensive logic rather than dead code. Two of the three files (`ledger-lib.sh`,
`mount-submodule.sh`) have prior `SECURITY`/`MED-004`-tagged comments documenting exactly why the
removed checks exist, which the PR description does not address at all — it only states *what*
was simplified, never *why* it's safe to remove. Reviewed against the actual failure paths (not
just the happy path), the ledger changes reintroduce silent data-loss/false-success bugs, and the
symlink change reintroduces the escape-bounds bug MED-004 was written to close.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:146-193` — `_write_ledger` no longer validates its input. The PR deletes both the pre-check (`[[ -z "$content" ]] || ! echo "$content" | jq empty`, base:152-156) and the post-stamp check (`[[ -z "$updated_content" ]]`, base:174-179). `_write_ledger` is invoked throughout this file from `if`/`&&`/`||` contexts by design — every caller is written as `_write_ledger "$x" || return $LEDGER_ERROR` (before this PR) specifically because the function returns `LEDGER_OK`/`LEDGER_ERROR` for callers to branch on. Per POSIX/bash `errexit` semantics, `set -e` is suspended for the entire command (including nested function calls) when it appears in an `if`/`&&`/`||`/`while` test — which is exactly how this library's own callers use it (e.g. `resolve_sprint_safe`'s `result=$(resolve_sprint "$input" 2>/dev/null) || { ... }` shows the same pattern elsewhere in this file). Concretely: if line 169's `jq --arg ts ... '.last_updated = $ts'` fails or emits empty output (e.g. because a caller's upstream `jq` pipeline silently produced malformed JSON, or `content` was already corrupt), `updated_content` becomes empty and is now written straight through to `$tmp_file` and atomically `mv`'d over `ledger_path` (lines 172-188) with no guard at all — the entire cycle/sprint ledger is replaced with an empty file, in-band, with no error returned to the caller.

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:379,418,459,511,601,822` — Every caller of `_write_ledger` (`create_cycle`, `update_cycle_field`, `allocate_sprint_number`, `add_sprint`, `update_sprint_status`, `archive_cycle`) drops the `|| return $LEDGER_ERROR` that used to follow the call. As above, whenever one of these functions is itself invoked from a caller's `if`/`&&`/`||`/`while` (the idiomatic way to consume a function that returns `LEDGER_OK`/`LEDGER_ERROR`), `errexit` is suspended for the whole call graph, so a failing `_write_ledger` (lock timeout, disk full, `mv` failure) no longer aborts anything — execution falls straight through to the subsequent `echo "$cycle_id"` / `return $LEDGER_OK`. Example: `create_cycle` (line 379) would `echo "$cycle_id"` and `return $LEDGER_OK` at line 381-382 even though the cycle was never persisted, so a caller doing `cycle_id=$(create_cycle "$label") || handle_error` gets a fabricated success and a cycle ID that doesn't exist in the ledger.

- **HIGH** (confidence: high) `head/.claude/scripts/ledger-lib.sh:576-603` — `update_sprint_status` no longer validates that `global_id` is numeric (base:590-594 removed this check before use in `jq --argjson id "$global_id"` at lines 592 and 596). `--argjson` requires a syntactically valid JSON value; a non-numeric `global_id` (e.g. an empty string, or `"UNRESOLVED"` propagated from a caller that didn't check `resolve_sprint`'s return) makes the `jq` invocation fail, so `ledger_content` becomes empty. That empty value is then handed straight to `_write_ledger` (line 601) which — per the first finding above — no longer refuses empty content, so this specific, previously-blocked input class (non-numeric sprint id) now has a direct path to truncating `ledger.json`.

- **HIGH** (confidence: high) `head/.claude/scripts/mount-submodule.sh:370-419` — `validate_symlink_target` drops its `source` (symlink location) parameter and its `resolve_base` logic, and instead tests `[[ -e "$target" ]]` / `dirname "$target"` directly. For a relative `target`, both of these resolve against the shell's *current working directory*, not the directory the symlink will actually live in — but real symlinks resolve relative targets against the symlink's own directory, which is exactly what the deleted `resolve_base=$(cd "$(dirname "$source")" && pwd)` (base:378-384) computed. Every call site (`create_symlinks`, lines 449-495) invokes `safe_symlink "$link_path" "$target"` with `cwd` at the repo root and `target` values like `"../$SUBMODULE_PATH/.claude/skills/foo"` meant to be read relative to `.claude/skills/`, not the repo root. Testing that path from the wrong base means `[[ -e "$target" ]]` and the `-d "$parent_dir"` fallback check paths that don't exist relative to cwd — even though the real, symlink-relative target does exist and is safely inside the repo — fall through to the `warn "Cannot resolve symlink target" ... return 0` branch at line 388, silently **allowing** the symlink with no bounds check at all. This defeats the MED-004 fix this function exists to implement: it can now both false-allow an escaping target (validated against the wrong path resolves as "in-bounds" by coincidence) and false-permit-via-bypass an unresolvable one that a correctly-based resolution would have validated correctly.

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/scripts/classify-pr-type.sh:64-66` — The rule matching `from [^ ]+/release/` and `^[Rr]elease(\([^)]*\))?:` titles (base:66-71) is deleted with no replacement and no rationale in the PR description (unlike the neighboring `^feat:` exclusion, which has an explanatory `NOTE` comment at lines 38-41 for why it's intentional). Per this file's own doc comment (lines 26-27, 30-34), `cycle` classification drives "CHANGELOG, GT, RTFM, Release run" in the post-merge pipeline. A PR titled e.g. `Release(v2.4.0): ship features`, or a merge-commit title `Merge pull request #999 from org/release/2.4.0`, now falls through to `bugfix`/`other` instead of `cycle`, silently skipping the full pipeline for what is actually a release merge. Flagging as an observation rather than blocking because I can't confirm from this diff alone whether release-merge routing is now handled elsewhere (e.g. purely by the "cycle-NNN" label/title rule instead) — but the PR description doesn't say so either, and should.
