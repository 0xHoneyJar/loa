# Review: chore(hooks,constructs): allow bounded hidden dirs, first-match local sources, strict traversal rejection

No sprint plan, beads database, or `grimoires/loa/a2a/` context exists for this evaluation — reviewed directly against `head.diff` / `base/` / `head/` as the entire input, per `REVIEW-INSTRUCTIONS.md`.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/constructs-lib.sh:565-593` — `find_local_source()` no longer verifies that a discovered local source path actually corresponds to the requested `slug`. The removed `_local_source_matches_slug` call was the only thing that connected the `slug` parameter to the `config_paths` branch (`constructs.local_source_paths` in `.loa.config.yaml`) — those entries are arbitrary user-configured directories, not slug-templated (unlike the `else` branch's hardcoded `.../construct-$slug` defaults at lines 582-585, where `$slug` is baked into the path itself). With the check removed, `slug` is dead in the `config_paths` path: the loop at lines 589-593 returns the *first* configured directory that merely contains a `construct.yaml` or `manifest.json`, regardless of which construct it actually is. A user with two or more entries in `constructs.local_source_paths` (e.g. sibling checkouts of different construct packs) will get pack A's directory returned when asking for pack B's slug, and the caller will silently install/update the wrong pack's code under the requested slug's identity. Failure scenario: `local_source_paths: ["~/dev/construct-alpha", "~/dev/construct-beta"]`, caller runs `find_local_source beta` — the loop returns `~/dev/construct-alpha` first because it exists and has a `construct.yaml`, and the caller proceeds to treat alpha's code as beta's local source. This is exactly the case the deleted function existed to prevent (matching declared `name`/`slug` in the manifest, or the directory's `construct-<slug>`/`<slug>` naming). No replacement verification was added, and no test file was touched in this PR to cover the new behavior.

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/scripts/lib/symlink-manifest.sh:258-259` — Replacing the resolve-and-normalize escape check with a blanket "any `..` segment in `link` or `target` is rejected" is a strictly more conservative rule than before, and functionally closes a real gap (the old code only ran `_path_has_traversal` on `link`, never on `target` directly). However it is also less permissive than the removed `_normalize_rel_path`-based check: a manifest entry where `target` legitimately contains `..` but resolves back inside the repo root (e.g. a construct nested two levels under `.claude/constructs/<pack>/sub/` pointing `../../shared/lib` at another in-repo `.claude/` location) is now unconditionally rejected, where before it was correctly allowed because the resolved path stayed under the repo root. This is a functional regression for any existing manifest relying on that pattern, not a security hole — flagging in case such manifests exist elsewhere in the repo (none are visible in this diff's touched files).
- **LOW** (confidence: medium) `head/.claude/hooks/safety/block-destructive-bash.sh:856` — The `\.env` alternative in `_re_allow_exclude` has no trailing `($|/)` boundary (unlike every other alternative in the same group: `\.git($|/)`, `\.ssh($|/)`, etc.), so it matches as a substring anywhere after `./`, not just an exact `.env`/`.env/` segment. `rm -rf ./.environment-backup/` or `rm -rf ./.env.local.old/` get pulled into the exclude branch (and thus AMBIGUOUS/blocked) purely because they start with the four characters `.env`, even though they're unrelated directories. This is fail-safe (over-blocks rather than under-blocks) so it isn't a security issue, just an inconsistency with the sibling patterns and a likely source of false-positive blocks/user confusion given this PR's stated goal (bd-m1o6/R-002) is specifically to *reduce* false positives on legitimate hidden-dir deletes.
- **LOW** (confidence: low) `head/.claude/hooks/safety/block-destructive-bash.sh:857` — The new hidden-dir allow branch `\./\.[A-Za-z0-9_-][^*]*` accepts any dot-directory name whose first character after the leading dot is alphanumeric/`_`/`-`, which also allows names like `./.aws-old`, `./.ssh_bak`, `./.gnupg2` that are one character away from the protected names in the exclude list. These are genuinely different paths from the protected ones (not a bypass of `~/.aws` etc.), but worth a second look if the intent was to protect by "family" of sensitive names rather than exact match.

## Overall Assessment

The `.env`-boundary and manifest-strictness observations are non-blocking. The `find_local_source` change, however, silently disconnects the function's `slug` argument from its own search logic in the (real, user-facing) `local_source_paths` configuration path, with no compensating check and no test coverage added — this needs a fix (restore a slug/declared-name verification step, or explicitly document/enforce that `local_source_paths` entries must be single-purpose per-slug and fail loudly on ambiguity) before merge.
