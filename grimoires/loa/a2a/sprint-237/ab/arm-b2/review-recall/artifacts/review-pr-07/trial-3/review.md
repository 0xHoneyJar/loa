- **HIGH** (confidence: high) `head/.claude/hooks/safety/block-destructive-bash.sh:856-857` — The new hidden-dir allowlist branch (`_re_allow_list`'s `\./\.[A-Za-z0-9_-][^*]*` alternative) permits `rm -rf` on any hidden path whose name is not in the curated `_re_allow_exclude` set. That exclude set enumerates `.git`, `.ssh`, `.aws`, `.kube`, `.gnupg`, `.docker`, `.config`, `.claude`, and `.env*`, but omits several common plaintext-credential locations: `.netrc`, `.npmrc`, `.pgpass`, `.git-credentials`, `.azure`, `.terraform`/`.terraformrc`, `.cargo/credentials`, `.pypirc`, `.boto`, `.s3cfg`. For example, `rm -rf ./.netrc` (or `rm -rf ./.azure/`) now falls through the exclude regex (no match) and matches the new allow branch, so it is silently permitted — where before this PR the old bare `\.` exclude alternative conservatively blocked *every* hidden path, including these. This is a straightforward denylist-completeness regression: the fix correctly widens access for the specific `.loa/`, `.cache/`-style paths called out in the incident report, but the same widening exposes every hidden credential file/dir not on the curated list to unprotected `rm -rf`. Concrete failure: an agent (or injected instruction) runs `rm -rf ./.netrc` from `$HOME` and the hook allows it, deleting saved network credentials that the pre-PR behavior would have blocked as ambiguous.
  - Suggested fix: either invert the approach (allow-list specific known-safe hidden dirs like `.loa`, `.cache`, `.git-hooks-cache` rather than deny-list known-sensitive ones), or extend `_re_allow_exclude` to cover the credential-file class generically (e.g. a pattern matching common secret-file names) in addition to the directory names already present.

- **HIGH** (confidence: high) `head/.claude/scripts/constructs-lib.sh:565-594` — `find_local_source` no longer verifies that the discovered directory's declared construct actually matches the requested `slug`; it now returns the *first* `search_paths` entry that merely contains a `construct.yaml`/`manifest.json`, regardless of which construct that manifest declares. This only stays safe by coincidence in the default-paths branch (lines 581-586), where every candidate path is itself built by interpolating `$slug` into the filename. It breaks the moment a user configures `constructs.local_source_paths` in `.loa.config.yaml` with more than one directory (the documented, intended use of that setting for local construct development): `find_local_source foo` and `find_local_source bar` will both return the *same* first valid directory in the configured list, silently substituting the wrong construct's local source for whichever slug was actually requested. The PR description confirms this is intentional ("returns the first existing local source path"), but the removed `_local_source_matches_slug` check (and its yq/jq-based declared-name lookup) was the only thing preventing a name/content mismatch — its loss turns this from "pick the right local clone" into "pick whichever clone happens to be listed/found first," which is a real correctness and supply-chain-adjacent risk for anyone with more than one local construct checkout configured.
  - Suggested fix: keep validating the declared slug (via `construct.yaml`'s `.name` / `manifest.json`'s `.slug`/`.name`) before accepting a `search_paths` entry, or restrict the simplification to only the slug-interpolated default paths and retain validation for user-configured `local_source_paths`.
