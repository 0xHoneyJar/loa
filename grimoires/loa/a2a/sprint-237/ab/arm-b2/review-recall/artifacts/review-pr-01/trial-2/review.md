# Review: chore(hooks,scripts): simplify carrier-value regexes, redaction patterns and sprint counting

## Overall Assessment

This "simplification" touches three security/state-integrity-sensitive shell helpers, and two of the three hunks introduce concrete regressions rather than neutral cleanups. The `workflow-state.sh` change reintroduces a classic `grep -c` double-output bug in the exact function the PR claims to be "restoring" to one-line output. The `invoke-diagnostics.sh` change silently drops AWS STS/IAM credential-shape coverage from a secret-redaction routine. The `block-destructive-bash.sh` change removes a documented multi-flag carrier mechanism, degrading (but not eliminating) the quote-blindness mitigation for the very common `gh pr create --title … --body …` shape. None of these are called out or justified in the PR description, which frames the whole diff as a no-op-risk cleanup.

## Changes Required

- **HIGH** (confidence: high) `head/.claude/scripts/workflow-state.sh:72` — `grep -c "^## Sprint [0-9]" "${SPRINT_FILE}" 2>/dev/null || echo "0"` prints two lines instead of one whenever `SPRINT_FILE` exists but contains zero matching `## Sprint N` headings. `grep -c` writes its count ("0") to stdout even when it finds no matches, and then exits with status 1 for "no lines selected" — which is exactly the case `2>/dev/null` and the trailing `|| echo "0"` do NOT suppress (stdout was already flushed; only the nonzero *exit status* trips the `||`). The result is stdout `"0\n0"` instead of `"0"`. Every caller assigns this via command substitution and uses it as an integer: `total_sprints=$(get_total_sprints)` is fed into `[[ "${completed_sprints}" -ge "${total_sprints}" ]]` (workflow-state.sh:151) and into `for ((i = 1; i <= total; i++))` inside `get_completed_sprints` (workflow-state.sh:86-88) and `for i in $(seq 1 "${total_sprints}")` (workflow-state.sh:158). A two-line value fed into an arithmetic context or `seq` argument breaks sprint-state detection (`determine_state`) the moment a sprint plan file exists before any `## Sprint N` section has been written — a realistic, easily-hit state. The base version's `n=$(grep -c ... || true); echo "${n:-0}"` avoided this precisely by capturing the already-flushed stdout into a variable before deciding what to print, so only ever one line was emitted. The PR description's claim that this "restores the one-line sprint count" is the opposite of what the diff does for the zero-match case.

- **HIGH** (confidence: high) `head/.claude/scripts/lib/invoke-diagnostics.sh:50` — the AWS credential-shape redaction pattern shrinks from `(AKIA|ASIA|AROA|AGPA|AIPA|ANPA|ANVA)[A-Z0-9]{16}` to `AKIA[A-Z0-9]{16}` only. This drops `ASIA*` — the prefix for AWS STS **temporary** access-key IDs, arguably the more commonly-leaked credential shape in modern assumed-role/CI environments — along with `AROA`/`AGPA`/`AIPA`/`ANPA`/`ANVA`. Concretely: an invoke-diagnostics log that previously would have redacted `ASIAABCDEFGHIJKLMNOP` to `ASIA***REDACTED***` will now pass it through to the log file (and whatever downstream consumer reads `setup_invoke_log`'s output) completely in the clear. This is a secret-redaction routine (`redact_secrets`, used to sanitize model-invoke failure logs) getting objectively less capable, framed in the PR as merely "trimmed back to the documented AWS access-key shape" — but the pre-existing code already redacted these prefixes; the "documentation" was added by this same PR to justify shrinking the pattern, not to describe pre-existing behavior.

## Observations

- **MEDIUM** (confidence: medium) `head/.claude/scripts/lib/invoke-diagnostics.sh:48` — the Bearer-token pattern narrows from `[A-Za-z0-9=._-]+` to `[A-Za-z0-9._-]+`, dropping `=`. RFC 6750 `b64token` values (and any base64-encoded opaque bearer token) can legitimately end in `=`/`==` padding. Since the character class still matches everything up to the padding, the practical effect is that 1-2 trailing padding characters survive redaction (e.g. `Bearer ***REDACTED***==`) rather than the whole token disappearing — low incremental leakage (padding carries no entropy) but it is a real narrowing of the character class with no stated rationale, and if a token ever contains a non-trailing `=` the match would truncate early and leave a longer non-padding suffix exposed.

- **MEDIUM** (confidence: medium) `head/.claude/hooks/safety/block-destructive-bash.sh:210-212` (compare against the removed `_bdb_re_tail` and its scrub loop, previously at base `.claude/hooks/safety/block-destructive-bash.sh:214,236-249` — `head/.claude/hooks/safety/block-destructive-bash.sh:220-241` after removal) — removing quote characters (`'"`) from the `[^;&|]*` prefix classes plus deleting the `_bdb_re_tail` multi-flag loop changes which carrier value gets redacted when a single git/br/bd/gh statement carries **two** redactable flags in one segment. Because bash's `[[ =~ ]]` performs POSIX leftmost-longest matching and quotes no longer block the prefix, the single remaining regex now greedily extends through the *first* flag+value and only redacts the *last* one it finds (e.g. in `gh pr create --title "..." --body "..."`, only `--body`'s value gets scrubbed; `--title`'s literal text is left fully visible in the scrub copy used for destructive-pattern matching). Previously the main regex + `_bdb_re_tail` tail loop redacted both. Net effect is a false-positive risk (a legitimate `gh pr create`/multi `-m` git commit whose *first* flag's text happens to contain a flagged destructive-sounding substring, e.g. a PR titled around "prevent accidental rm -rf", now risks being blocked) rather than a bypass — the fence still fails toward blocking, consistent with its fail-safe design goal — but it silently narrows a feature (multi-flag inert-carrier redaction) that the file's own extensive commentary treats as adversarially load-bearing, for the single most common two-flag invocation (`gh pr create --title … --body …`) in this very toolchain's own PR-authoring convention.
