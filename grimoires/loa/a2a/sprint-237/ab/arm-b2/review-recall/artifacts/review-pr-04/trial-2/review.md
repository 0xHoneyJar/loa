# Review: chore(cheval,flatline,status): shorten headless env scrub, temp-file handling, flag parsing

## Summary

This PR frames itself as a pure simplification/"chore," but two of the three hunks remove
functional safeguards rather than just tidying code: the cheval headless env scrub drops a
documented security-relevant var class (reopening the exact class of bug fixed by issues
#879/#880 for Gemini), and the flatline-orchestrator `mktemp` guards are removed even though
`set -euo pipefail` means a mktemp failure now aborts the whole orchestrator run instead of
degrading gracefully. The loa-status.sh changes are a real behavior regression too (colors
forced on for non-tty/`NO_COLOR` consumers, unknown-flag validation dropped).

## Changes Required

- **HIGH** (confidence: high) `head/.claude/adapters/loa_cheval/providers/base.py:472-478` — `_HEADLESS_STRIPPED_AUTH_VARS` drops `GOOGLE_GENAI_USE_VERTEXAI`, `GOOGLE_GENAI_USE_GCA`, `GOOGLE_GEMINI_BASE_URL`, and `GEMINI_CLI_USE_COMPUTE_ADC`, while the comment directly above (`head/.claude/adapters/loa_cheval/providers/base.py:466-471`, unchanged by this PR) still explains *why* they must be stripped: "if any of these vars are exported in the parent process the CLI falls back to API mode — defeating the headless adapter's purpose." These four vars are exactly the Gemini CLI's auth-mode selectors (Vertex AI / GCA / compute-ADC routing), not credentials — the same "auth-mode-selector sub-class" the pre-PR docstring at `base/.claude/adapters/loa_cheval/providers/base.py:483-491` explicitly called out as distinct from the credential sub-class and equally in-scope. Concretely: an operator with `GOOGLE_GENAI_USE_VERTEXAI=1` (or `GEMINI_CLI_USE_COMPUTE_ADC=1`) set in their shell for unrelated Vertex work will now have that var leak into every headless Gemini subprocess launched via `build_headless_subprocess_env`, silently rerouting the CLI off its OAuth-subscription path — reopening issues #879/#880 for Gemini specifically. The PR description ("simplifies... env scrub") gives no rationale for dropping these vars, and the surrounding comment block was left inconsistent with the code (it still says the stripping is auth-class-wide, closes #879/#880) rather than updated to justify the narrowing. This needs either the four vars restored, or an explicit, reviewed justification (and a matching comment update) for why the auth-mode-selector class is now considered safe to leave in place.

## Observations

- **MEDIUM** (confidence: high) `head/.claude/scripts/flatline-orchestrator.sh:577` and `head/.claude/scripts/flatline-orchestrator.sh:2282` — both unguarded `mktemp` calls sit under `set -euo pipefail` (`head/.claude/scripts/flatline-orchestrator.sh:47`). The removed `if ! tmp=$(mktemp ...); then ... continue; fi` wrapper was doing real work: because the check lived inside an `if`, it was exempt from `set -e`, so a transient mktemp failure (full/read-only `/tmp`, hit inode quota, etc.) logged a warning and skipped just that one verdict-quality envelope or arbiter step. With the guard removed, the same failure is a bare `tmp=$(mktemp ...)` assignment outside any conditional, so under `set -e` it now aborts the entire flatline-orchestrator run for every phase/voice in flight rather than degrading one item. This trades a documented graceful-degradation path for a hard failure; worth confirming that's the intended tradeoff before merging, since `/tmp` capacity/permission issues are a realistic real-world trigger in CI/sandboxed environments.
- **MEDIUM** (confidence: high) `head/.claude/scripts/loa-status.sh:30-35` — colors are now assigned unconditionally, dropping the prior `[[ -z "${NO_COLOR:-}" ]] && [[ -t 1 ]]` guard (`base/.claude/scripts/loa-status.sh:26-40`). Any consumer that redirects/pipes `loa-status.sh` output (log files, CI capture, `| grep`, other scripts parsing the text) now gets raw ANSI escape sequences embedded in the output, and setting `NO_COLOR=1` no longer has any effect. This is a real regression for any non-interactive caller of the script, not just a stylistic simplification.
- **LOW** (confidence: high) `head/.claude/scripts/loa-status.sh:43-65` — the unknown-flag rejection path (previously tracked via `UNKNOWN_ARGS` and `dx_unknown_flag`/usage-line exit 2 in `base/.claude/scripts/loa-status.sh:92,105-115`) is gone. Outside `--economy` mode, an unrecognized flag (e.g. a typo like `--jsno`) is now silently absorbed into the unused `ECONOMY_ARGS` array and the script proceeds to print normal status with exit 0, instead of failing fast with a usage message. This could mask caller typos in scripts/CI that previously would have been caught immediately.
- **LOW** (confidence: medium) `head/.claude/adapters/loa_cheval/providers/base.py:484-486` — the trimmed docstring no longer distinguishes the "credential" vs. "auth-mode-selector" sub-classes it used to call out explicitly (`base/.claude/adapters/loa_cheval/providers/base.py:487-491`). Even independent of the HIGH finding above, this loses documentation value: a future editor of `_HEADLESS_STRIPPED_AUTH_VARS` has less context for why any given var belongs in the tuple.

## Verdict

Changes required — the cheval env-scrub narrowing reopens a previously-fixed, documented security-relevant bug for Gemini headless mode. The flatline-orchestrator and loa-status.sh items are not blocking on their own but should be addressed or explicitly justified before this ships as a "chore."
