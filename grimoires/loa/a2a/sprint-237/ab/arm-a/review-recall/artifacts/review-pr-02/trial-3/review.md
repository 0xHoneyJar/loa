# Review: refactor(audit,spiral,semver): drop strict-verify plumbing, backtick masking and prerelease branches

## Overall Assessment

**CHANGES REQUIRED.** The PR frames itself as dead-code cleanup ("single code path again"), but the `audit_envelope.py` hunk actually deletes a security control (merge-gate strict trust-store/signature verification) whose inline comments explicitly tie it to named attack scenarios (ATK-3, ATK-4) and issue #690. The removal is silent at the interface that matters most: an external caller that sets `LOA_AUDIT_STRICT_VERIFY=1` to gate a merge no longer gets an error — it just gets weaker verification with no indication anything changed. That is a fail-open regression, not a simplification, and it needs an explicit justification (or a revert) before this can land. The `spiral-evidence.sh` hunk also reintroduces a false-positive class (#1175) that a sibling guard in the same function exists specifically to prevent. The `semver-bump.sh` hunk is the most defensible of the three but still deserves a sanity check against existing tag history.

## Critical Issues

### 1. Security control silently disabled: `LOA_AUDIT_STRICT_VERIFY` becomes a no-op instead of erroring or being removed end-to-end

`head/.claude/adapters/loa_cheval/audit_envelope.py:508` — `audit_verify_chain()` no longer reads `LOA_AUDIT_STRICT_VERIFY` at all (the whole `_strict_verify_enabled()` function at `base/.claude/adapters/loa_cheval/audit_envelope.py:136-138` is deleted with no replacement). Any external script (CI merge-gate, `/audit-sprint`, a pre-merge hook — none of which are in this diff's scope, so their existence can't be ruled out) that sets that env var expecting strict verification will now silently get the lenient path. Before this change, strict mode refused three cases the lenient path accepts:

- `head/.claude/adapters/loa_cheval/audit_envelope.py:462-473` (`_check_trust_store`) — `BOOTSTRAP-PENDING` now always passes (`status in ("BOOTSTRAP-PENDING", "VERIFIED")`). The deleted code at `base/.claude/adapters/loa_cheval/audit_envelope.py:477-482` refused `BOOTSTRAP-PENDING` under `strict_verify` with `[TRUST-STORE-BOOTSTRAP-PENDING] ... refuses BOOTSTRAP-PENDING (ATK-3)`. ATK-3 is presumably "attacker prevents trust-store bootstrap to keep verification permanently lenient" — that attack is unmitigated again for any caller that used to rely on strict mode.
- `head/.claude/adapters/loa_cheval/audit_envelope.py:476-494` (`_read_trust_cutoff`) — a missing or unreadable trust-store now just returns `None` (no cutoff) instead of raising `[TRUST-STORE-MISSING]` / `[TRUST-STORE-UNREADABLE]` (ATK-4, `base/.claude/adapters/loa_cheval/audit_envelope.py:500-506, 513-516`). A missing trust-store silently grandfathers every entry instead of blocking.
- `head/.claude/adapters/loa_cheval/audit_envelope.py:136-160` (`_resolve_pubkey_pem`) — local `<key-dir>/<key_id>.pub` fallback is now unconditional (`allow_local_fallback` parameter deleted). The strict path used to pass `allow_local_fallback=not strict_verify` (`base/.claude/adapters/loa_cheval/audit_envelope.py:609`) specifically so merge-time verification could only resolve pubkeys through the signed trust-store, not an arbitrary local file. An attacker with filesystem write access to `LOA_AUDIT_KEY_DIR` can now always mint a signer that chain-verification will accept, even at merge time.

**Failure scenario:** a merge-gate script does `audit_verify_chain(log_path, verify_for_merge=True)` or sets `LOA_AUDIT_STRICT_VERIFY=1` before invoking it, expecting a tampered/unbootstrapped/unsigned trust-store to hard-fail the merge. After this change, that call either throws (see Critical #2) or — if the caller only sets the env var and doesn't pass the kwarg — succeeds silently on exactly the inputs strict mode was built to reject. Either way the merge-time guarantee referenced by issue #690 is gone, and nothing in this diff, or in the PR description, demonstrates that guarantee is no longer needed.

## High-Severity Issues

### 2. Breaking change to a public function signature with no caller audit shown

`head/.claude/adapters/loa_cheval/audit_envelope.py:508` — `audit_verify_chain(log_path: PathLike)` drops the keyword-only `verify_for_merge: bool = False` parameter entirely (was `base/.claude/adapters/loa_cheval/audit_envelope.py:532`). `audit_verify_chain` is exported in `__all__` (`head/.claude/adapters/loa_cheval/audit_envelope.py:642-648`) as public API, and the module docstring at `head/.claude/adapters/loa_cheval/audit_envelope.py:1-22` explicitly claims parity with the bash adapter for external callers. Any caller outside this diff's file scope that passes `verify_for_merge=True` now gets `TypeError: audit_verify_chain() got an unexpected keyword argument 'verify_for_merge'` — a hard crash where before it may have been a hard security refusal. The PR description doesn't show a grep for callers of `verify_for_merge=`/`LOA_AUDIT_STRICT_VERIFY` confirming they're unused; given the specificity of the ATK-3/ATK-4 comments this function was very likely written *for* a merge-gate caller.

## Medium-Severity Issues

### 3. `spiral-evidence.sh` reintroduces the exact false-positive class issue #1175 was fixed to prevent

`head/.claude/scripts/spiral-evidence.sh:700` — Pattern 2 now scans raw `$content` instead of `$content_bare` (the backtick-stripped copy deleted at `base/.claude/scripts/spiral-evidence.sh:673-674`). The comment directly above Pattern 1's own false-positive guard, still present at `head/.claude/scripts/spiral-evidence.sh:683-687`, explains the exact hazard: "backtick prose also wraps shell commands (`bash tools/x.sh`, `yq -o=json ... file.yaml`) and CLI flags ... that contain `/`+extension and matched as deliverable paths, failing cycles with IMPL_EVIDENCE_MISSING." That guard (`grep -v whitespace|glob|leading -/@`, `head/.claude/scripts/spiral-evidence.sh:688-690`) only filters Pattern 1's output. Pattern 2 has no such filter, and `grep -oE` extracts substrings, not whole lines, so it doesn't need the input to lack whitespace — it just needs the path-shaped substring to be present anywhere in the line. A sprint.md sentence like `` Run `bash tests/e2e/checkout.spec.ts --update-snapshots` to verify `` previously had its entire backtick span erased by `content_bare` before Pattern 2 ran, so Pattern 2 never saw it. Now Pattern 2 will extract `tests/e2e/checkout.spec.ts` as a claimed deliverable path from what is actually a shell-command example. Since output is deduped via `sort -u` (`head/.claude/scripts/spiral-evidence.sh:703`), this doesn't add *new noise* when the same path also legitimately appears as a real backtick-wrapped path (Pattern 1 already catches those) — but it does reopen the false-positive path for command examples that reference real source-tree paths inside example commands, which is precisely the #1175 scenario the guard names. Worth a regression test asserting a backtick-quoted shell command doesn't produce a deliverable-path match via Pattern 2.

### 4. `semver-bump.sh` prerelease removal can silently skip an in-progress prerelease line

`head/.claude/scripts/semver-bump.sh:55-63` (`get_version_from_tag`) now filters to `v[0-9]*.[0-9]*.[0-9]*` only (an fnmatch pattern, so it correctly excludes tags like `v2.0.0-beta.2` since there's no trailing `*` to absorb the suffix). Combined with `head/.claude/scripts/semver-bump.sh:80-94` (`bump_version`) now rejecting any non-`M.m.p` input, this is consistent and won't crash — but it changes semantics for a repo that currently has a prerelease tag as its most recent tag. Example: tags are `v1.9.0` (release) then `v2.0.0-beta.2` (later, prerelease). Before this PR, `get_version_from_tag` would consider both, `--sort=-v:refname` would rank `v2.0.0-beta.2` above `v1.9.0`, and the next computed version would continue the beta line. After this PR, `v2.0.0-beta.2` is invisible to `get_version_from_tag`; the tool picks `v1.9.0` as current and computes something like `v1.10.0` or `v2.0.0` from there — a version that can collide with or be lower than the already-published `v2.0.0-beta.2`, and commits already covered by the beta tag get re-counted via `git rev-list "${tag_ref}..HEAD"` against the wrong base tag. This may be intentional per the PR title ("returns ... to release-only version parsing"), but the PR doesn't state whether any prerelease tags currently exist in tag history, and this file has no test fixture exercising that case in the diff. Please confirm there are no live prerelease tags this would strand, or note the migration/cutover explicitly.

## Adversarial Analysis

### Concerns Identified
1. `LOA_AUDIT_STRICT_VERIFY` becomes a silent no-op instead of being removed loudly or kept — `head/.claude/adapters/loa_cheval/audit_envelope.py:508`.
2. `audit_verify_chain`'s public signature drops `verify_for_merge` with no shown caller audit — `head/.claude/adapters/loa_cheval/audit_envelope.py:508`.
3. `_resolve_pubkey_pem` now always allows local-file pubkey fallback, closing off the one mode that forced trust-store-only key resolution — `head/.claude/adapters/loa_cheval/audit_envelope.py:136-160`.
4. `spiral-evidence.sh` Pattern 2 loses the backtick-stripping that guarded against the #1175 false-positive class — `head/.claude/scripts/spiral-evidence.sh:700`.

### Assumptions Challenged
- **Assumption**: The engineer's framing ("drop strict-verify plumbing... single code path again") treats this as removing unused/redundant complexity.
- **Risk if wrong**: The comments this PR deletes (`ATK-3`, `ATK-4`, issue #690, "strict audit verification refuses BOOTSTRAP-PENDING") read like the output of a prior security review that specifically hardened merge-time verification. If any merge gate or `/audit-sprint`-adjacent tooling still relies on `verify_for_merge=True` or `LOA_AUDIT_STRICT_VERIFY=1`, this PR reopens exactly the attack surface that hardening closed — and does so silently for the env-var path, which is worse than a loud break.
- **Recommendation**: Before merging, grep the full repo (not just this diff's three files) for `verify_for_merge`, `LOA_AUDIT_STRICT_VERIFY`, and `allow_local_fallback` to prove no caller depends on strict mode. If none exist, say so explicitly in the PR description with the grep evidence. If any do, this is not a safe refactor as written.

### Alternatives Not Considered
- **Alternative**: If the strict-verify path really is dead code, delete it with a one-line PR note showing the grep that proves zero callers (repo-wide, not just this diff), rather than presenting it as a self-evident simplification.
- **Tradeoff**: A grep-verified removal costs one extra command and a sentence in the PR description; an unverified removal risks silently re-opening a documented attack surface (ATK-3/ATK-4) with no test coverage change to catch the regression.
- **Verdict**: Should reconsider — request the caller audit before approving, or split this into (a) the `spiral-evidence.sh`/`semver-bump.sh` hunks, which are independently reviewable and lower-risk, and (b) the `audit_envelope.py` hunk, gated on caller verification.
