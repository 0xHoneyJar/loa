## Summary

The five follow-ups are implemented as the SDD specifies and every acceptance test was red first. The work is good; three findings require a round before approval, all in the security posture the cycle exists to improve. **(1)** The base-sha `.reviewignore` read fails *open*: when the base commit is not in the reviewer's clone (the common CI checkout, a stale local main, a different `--repo`), the read yields `none` and **no** `.reviewignore` pattern applies — the operator's deny list for secrets and private paths, which the checkout read always applied before this sprint, is dropped silently (dissent A, BLOCKING). **(2)** "An explicit name wins over protection" is implemented as "any non-wildcard pattern wins": a floating segment line such as `ci.yml`, `workflows` or `.github` removes `.github/workflows/ci.yml` or `.claude/settings.json` with no record (dissent A). **(3)** `protected_paths`, `exclude_patterns`, `fetch_missing_patches` and `max_content_fetches` are read from the checkout's `.loa.config.yaml`, which on a pull-request checkout is the PR head: a PR can set `protected_paths: []` and exclude its own workflow change — the trusted-config precedence that provider keys already use (`BRIDGEBUILDER_TRUSTED_CONFIG` → base ref → `origin/main`) must govern these keys too (dissent A). Two further items change behaviour and are folded into the round: wildcard patterns without `/` are root-anchored while non-wildcard ones float (`*.pem` vs `PROCESS.md`), an asymmetry a `.reviewignore` author with gitignore habits will misread; and findings on a file reviewed from contents may carry inline anchors GitHub cannot place, which fails the whole review post (dissent B).

## Findings

- **HIGH** (confidence: high) `.claude/skills/bridgebuilder-review/resources/core/truncation.ts:529` — `readBaseReviewignore` turns every failure into `source: "none"` with zero patterns. Failure: when the base commit is absent from the local clone (a shallow or fetch-less checkout, a stale local main), then `secrets/` and `vendor/` lines the operator relies on are not applied and their content reaches the model. Fix: on a failed base read apply the **checkout** patterns and report `source: "base_unavailable"` (the lead adds the value to `CoverageRecord`); the record degrades with the new reason `reviewignore_unavailable` (merge-blocking) so a hidden PR-head edit cannot pass unnoticed, and the summary says so. `none` only when neither base nor checkout has the file. A follow-up bead takes the contents-API read of the base `.reviewignore`.
- **HIGH** (confidence: high) `.claude/skills/bridgebuilder-review/resources/core/truncation.ts:343` — `partitionUserExclusions` (and SKILL.md's protected-paths heading) takes "explicit" to mean any non-wildcard pattern. Failure: when a `.reviewignore` holds `ci.yml` or `.github`, then `.github/workflows/ci.yml` is excluded with no `protectedKept` entry. Fix: explicit = a root-anchored non-wildcard pattern (contains `/` after normalisation) or one equal to the protected file's full path; a floating segment pattern is treated like a wildcard for protection (kept, recorded with that pattern); tests with `ci.yml`, `.github`, `settings.json`; document with those examples.
- **HIGH** (confidence: medium) `.claude/skills/bridgebuilder-review/resources/config.ts:1570` — the four exclusion-affecting keys are resolved from the checkout YAML only. Failure: when a PR's `.loa.config.yaml` sets `protected_paths: []` (or `fetch_missing_patches: false`, or adds an `exclude_patterns` entry naming its workflow), then that PR's own review honours it. Fix: resolve `protected_paths`, `exclude_patterns`, `fetch_missing_patches` and `max_content_fetches` through the existing trusted-config precedence (`loadTrustedConfig`: repository settings → base ref → `origin/main`) when a trusted source resolves; the head's values for those keys are ignored with one WARN naming the drift; a run with no trusted source behaves as today (local dry runs). Tests both ways.
- **MEDIUM** (confidence: medium) `.claude/skills/bridgebuilder-review/resources/core/truncation.ts:121` — `translateGlobSegment` / `compileGlob` root-anchor a wildcard pattern without `/`: it is root-anchored (`*.pem` matches `a.pem`, not `keys/a.pem`) while a non-wildcard pattern without `/` floats. Failure: when a `.reviewignore` holds `*.key`, then nested keys stay in the review set although the author believes they are excluded. Fix: a wildcard pattern without `/` gets an implicit leading `**/` (gitignore semantics); grammar comment and SKILL.md state it with the `*.pem` / `**/*.pem` example; tests both ways (a protected path matched by such a floating wildcard is kept — the protection rule still applies).
- **MEDIUM** (confidence: medium) `.claude/skills/bridgebuilder-review/resources/core/reviewer.ts:367` — review submission: a finding on a file reviewed from contents (`reviewed[].source == "contents"`) may carry an inline `path`/`line` anchor GitHub cannot place on a file it served no patch for. Failure: when the model anchors one finding on such a file, then the review POST returns 422 and nothing is posted. Fix (B, allowlist extended to `reviewer.ts` for this one change): findings on contents-sourced files are emitted body-only (no inline anchor) unless the submission path already degrades per comment — B reads `postReview`'s 422 handling and reports which; test through the stub `gh`.
- **MEDIUM** (confidence: high) `.claude/skills/bridgebuilder-review/resources/core/paged-fetch.ts:240-283` — `fetchMissingPatches`: a `RATE_LIMITED` or `FORBIDDEN` provider error is swallowed per file and the loop keeps issuing calls. Failure: when the token lacks contents read, then up to twenty `gh api` calls fail identically before pass 2 fails the same way. Fix: on `RATE_LIMITED`/`FORBIDDEN` record `error` for the current file and `aborted` (new outcome, lead adds it) for the remaining eligible files without further calls; two-file test asserting one call.
- **MEDIUM** (confidence: medium) `.claude/skills/bridgebuilder-review/resources/core/paged-fetch.ts:350-356` — a successful read that does not fit because GitHub patches ahead of it already consumed the budget is labelled `too_large`, the same label as `encoding: none` and a buffer overflow; and the read was issued although it could never fit. Failure: when a small added file follows large GitHub patches in selection order, then the record shows `fetch: too_large` for a file whose content read succeeded, and a provider call was spent on a patch that could never be kept. Fix: compute `remaining` after the GitHub patch bytes already selected ahead of the file (prefix sum over `sel.included` in selection order), skip the read without a call when it cannot fit, and record the distinct outcome `budget` (lead adds it).
