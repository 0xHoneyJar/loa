# Task: cron schedules and rule zones for cronq

`cronq` (under `src/cronq/`) is a small job scheduler driven by a simulated clock. Jobs come from a jobs file (`cronq.jobs.parse_jobs`), zones from a zone table file (`cronq.zones.parse_zones`), settings from an optional config file (`cronq.config.parse_config`). A schedule answers `next_after(instant, zone)`: the first fire instant strictly after `instant`. Instants are integer seconds since 1970-01-01T00:00:00Z; a zone is an initial offset plus transitions (`Zone.initial`, `Zone.changes`, `Zone.offset_at(instant)`: the offset in effect at an instant is that of the last transition at or before it). Today the only schedule is the interval (`every 15m`). Add cron schedules, their backward and counting queries, and zones given as rule strings, exactly as specified below. Read the existing modules first: the runner's catch-up rule, the agenda format and the error conventions stay as they are.

## API

- `cronq.cron.parse_cron(text, horizon_days=1830)` returns a `cronq.cron.CronSchedule`; every problem raises `cronq.errors.CronError`, a new subclass of `ScheduleError`. `CronError`, `CronSchedule` and `parse_cron` are also importable from `cronq`.
- `CronSchedule.next_after(instant, zone)` returns an instant (a whole minute) or raises `CronError` (see Horizon).
- `CronSchedule.prev_before(instant, zone)`, `CronSchedule.count_between(start, end, zone)` and `CronSchedule.nth_after(instant, n, zone)` (rules 21–23).
- `cronq.zones.parse_tz(text, name="TZ")` returns a `Zone` built from a rule string (rules 24–31), also importable from `cronq`.
- `CronSchedule.matches(wall)` takes a naive `datetime.datetime` (a local wall time) and returns whether its minute, hour, day and month match the expression (seconds ignored; no zone involved).
- `CronSchedule.describe()` returns `cron ` followed by the expression's five fields joined by single spaces, or `cron ` followed by the macro as written (stripped).
- `cronq.schedule.parse_schedule` accepts `cron <expression>`: the schedule text, stripped, minus its leading word `cron`, is parsed by `parse_cron` with the given `horizon_days`. So a jobs line `backup | Lakeland | cron 30 2 * * * | run-backup` works, and a bad expression in a jobs file reports `jobs:<line>: bad schedule: <CronError message>` through the existing jobs error path. The config's `horizon_days` reaches every cron job of the jobs file.

## Expression syntax

1. The text is stripped of surrounding whitespace. An empty result: `empty expression`.
2. If it starts with `@` it is a macro, matched case-insensitively against the whole stripped text: `@yearly` and `@annually` = `0 0 1 1 *`, `@monthly` = `0 0 1 * *`, `@weekly` = `0 0 * * 0`, `@daily` and `@midnight` = `0 0 * * *`, `@hourly` = `0 * * * *`. Anything else starting with `@`: `unknown macro <repr>` (the repr of the stripped text, e.g. `unknown macro '@daily x'`).
3. Otherwise it splits on runs of whitespace into fields; not exactly five: `expected 5 fields, got <n>`.
4. The fields, in order, are field 1 `minute` (0-59), field 2 `hour` (0-23), field 3 `dom` (day of month, 1-31), field 4 `month` (1-12), field 5 `dow` (day of week, 0-7, where both 0 and 7 are Sunday).
5. Fields are checked left to right and the first problem is reported as `field <n> (<name>): <reason>`, e.g. `field 3 (dom): value 32 out of range 1-31`.
6. A field is a list of items separated by `,`; items are checked left to right. An empty item (as in `1,,2` or `5,`): `empty item`.
7. A *value* is one or more ASCII digits (leading zeros allowed, `05` is 5) or, in `month` only, a month name `JAN` … `DEC`, and in `dow` only, a day name `SUN` … `SAT` (0 … 6); names are case-insensitive. Anything else: `bad value <repr>` (the repr of that text). A value outside the field's range: `value <v> out of range <low>-<high>` (`<v>` the integer, `<low>-<high>` the field's range from rule 4).
8. Special items, recognised only when the WHOLE item has one of these shapes (letters case-insensitive), are checked before the ordinary forms:
   - in `dom`: `L` (the last day of the month); `LW` (the last weekday, Monday–Friday, of the month); `<digits>W` with ASCII digits (the weekday nearest to that day, rule 15) — its number is a value of the `dom` range;
   - in `dow`: `<d>L` (the last `<d>` of the month) and `<d>#<k>` (the `<k>`-th `<d>` of the month), where `<d>` is one or more ASCII digits or exactly three ASCII letters, checked as a `dow` value (so `XYZL` gives `bad value 'XYZ'`), and `<k>` is one or more ASCII digits checked after `<d>`: outside 1-5 gives `occurrence <k> out of range 1-5`.
   Any other item (for example `L` in `dow`, `L/2`, `5L` in `dom`, `MON#x`) is an ordinary item and is checked by rule 9.
9. An ordinary item is `<base>` or `<base>/<step>`, split at the first `/`. The base is checked first, then the step.
   - Base `*`: the whole field range. Base containing `-`: split at the first `-` into a start and an end value; the start is checked completely by rule 7 before the end; start greater than end: `reversed range <repr of the base>` (no wraparound; `FRI-MON` is reversed, `5-7` is Friday through Sunday). Otherwise a single value; with a step, `a/s` means `a` through the field's maximum.
   - The step is one or more ASCII digits, else `bad step <repr>` (so `*/` gives `bad step ''` and `*/MON` gives `bad step 'MON'`: names are never steps); a step of zero: `step must be at least 1`.
   - The item selects start, start+step, … up to the end. A step larger than the range selects only the start.
10. A field is *unrestricted* exactly when its text is `*`. Anything else — including `*/1`, `*,5` and `0-7` — is restricted.

## Matching a day and a minute

11. A wall minute matches when its minute is selected by field 1, its hour by field 2, its month by field 4, and its day matches by rule 12.
12. Day rule: if `dom` and `dow` are both restricted, the day matches when EITHER matches; if only one is restricted, that one decides; if neither is, every day matches. `dom` matches a day when an ordinary item selects its number or a special item (rule 8) picks it; a day number the month does not have never matches (`31` never fires in April). `dow` matches when an ordinary item selects its weekday (7 counts as Sunday) or a special item picks it.
13. `<d>L` picks the day of weekday `<d>` that has no later day of the same weekday in the month.
14. `<d>#<k>` picks the day of weekday `<d>` whose number is in `7(k-1)+1 … 7k`; a month without a fifth one has no match for `#5`.
15. `<n>W`: if the month has no day `<n>` the item picks nothing that month. Otherwise, if day `<n>` is Monday–Friday it is picked; if it is a Saturday, the Friday before is picked, except that for day 1 the Monday after (day 3) is picked; if it is a Sunday, the Monday after is picked, except that for the month's last day the Friday before (two days earlier) is picked. The pick never leaves the month.

## Next fire, zones and the horizon

16. Matching uses the local wall time of the job's zone: the instant plus the offset in effect at it.
17. `next_after(instant, zone)` returns the earliest whole-minute instant strictly after `instant` (so `10:15:30` gives at least `10:16:00`, and `10:15:00` gives at least `10:16:00`) whose wall time matches and whose wall time did not already occur at an earlier instant. Consequences: a wall time that a forward offset change skips never fires on that day (it is not moved), and a wall time that a backward offset change repeats fires only at its first occurrence. The rule applies across the whole timeline: if `instant` lies within the repeated stretch, wall times whose first occurrence is before `instant` do not fire again.
18. Horizon: only instants at most `horizon_days × 86400` seconds after `instant` are candidates. When none fires: `CronError("no fire time within <horizon_days> days")`.
19. Agenda and runner: a cron job that runs out of fire times within its horizon simply has no further fires. `build_agenda` lists the fires it does have (and nothing for it after that) and the runner records nothing more for it; neither raises.

## Earlier fires, counts and the n-th fire

Let **F** be the set of fire instants of an expression in a zone: every whole-minute instant whose wall time matches and whose wall time did not already occur at an earlier instant — exactly the instants rule 17 fires on, over the whole timeline. `next_after(t)` is the smallest element of F in `(t, t + horizon_days × 86400]`. All instants below are integers; the bounds are exact.

21. `prev_before(instant, zone)` returns the largest element of F in `[instant − horizon_days × 86400, instant)`. When there is none: `CronError("no fire time within <horizon_days> days before")`.
22. `count_between(start, end, zone)` returns the number of elements of F in `(start, end]` (so `count_between(t, t, zone)` is 0). `end < start`: `CronError("end before start")`; `end − start > 1096 × 86400`: `CronError("span longer than 1096 days")` (that check comes second). `horizon_days` plays no part.
23. `nth_after(instant, n, zone)` returns the `n`-th smallest element of F in `(instant, instant + 1096 × 86400]` (`nth_after(t, 1, zone)` is the smallest). `n < 1`: `CronError("n must be at least 1")`; fewer than `n` elements: `CronError("fewer than <n> fire times within 1096 days")`. `horizon_days` plays no part.

## Rule zones

24. In the zone table file a zone may consist of exactly one entry `rule <TEXT>` instead of `initial` and transition lines (`zone Eastern` then `  rule EST5EDT,M3.2.0/2,M11.1.0/2`). A problem in the text is reported as `zones:<line>: <reason>` with the reasons of rule 31. A second `rule` line in a zone: `zones:<line>: second rule`; a `rule` line in a zone that already has `initial` or transition entries, or such an entry after a `rule` line: `zones:<line>: rule and table entries cannot be mixed`. `parse_tz(text, name)` raises `ZoneError(<reason>)` with the bare reason.
25. Grammar (the text is stripped first; nothing else may appear, whitespace included): `STD OFFSET` for a zone that is always standard time, or `STD OFFSET DST [OFFSET] ,START[/TIME],END[/TIME]`. Unlike POSIX, the two rules are required whenever a daylight name is given.
26. A name (`STD`, `DST`) is either the longest run of ASCII letters at that point, at least three of them, or `<` followed by at least three ASCII letters, digits, `+` or `-` and then `>` (`<+0330>`, `<-03>`).
27. `OFFSET` is `[+|-]h[:mm[:ss]]`: `h` is one or two ASCII digits with value 0..24, `mm` exactly two digits 00..59, `ss` exactly two digits and must be `00`; each number is the longest run of digits at that point. **Sign: a POSIX offset is what you add to local time to get UTC, the negation of cronq's east-positive offsets:** `EST5` is −05:00, `<+0330>-3:30` is +03:30, `UTC0` is +00:00. A daylight name without an offset means one hour ahead of standard time (cronq offset = standard + 60 minutes).
28. `START` and `END` are dates: `J<n>` with `n` 1..365 (one to three digits) is day `n` of the year counting January 1 as 1 and never counting February 29 (`J60` is March 1 in every year); `<n>` with `n` 0..365 (one to three digits) is January 1 plus `n` days, counting February 29 (in a common year `365` is January 1 of the next year); `M<m>.<w>.<d>` with `m` 1..12 (one or two digits), `w` 1..5 and `d` 0..6 (one digit each, 0 = Sunday) is the `w`-th day `d` of month `m`, where `w = 5` means the last day `d` of the month (the fourth when there is no fifth).
29. `TIME` is `[+|-]h[:mm[:ss]]` with `h` one to three digits 0..167 (`mm`, `ss` as in rule 27), default `2` (02:00). It is a local time counted from midnight starting the date and may be negative or exceed 24 hours, moving the moment to another day (`/-1` is 23:00 the day before, `/26` is 02:00 the day after). The start moment is read in standard time, the end moment in daylight time: the start transition instant is that local moment minus the standard offset, the end transition instant that moment minus the daylight offset.
30. The zone: `initial` is the standard offset; `changes` lists, for every year 1970 through 2199, the start transition (to the daylight offset) and the end transition (to the standard offset), all sorted by instant, a start before an end at the same instant. Southern-hemisphere rules (start later in the year than end) need nothing special. A standard-only zone has no changes. Everything else (`offset_at`, the agenda, cron matching) treats it like a table zone.
31. Rule-string errors, checked in this order, the first one found being the reason: empty text: `empty rule`; a bad standard name: `bad std name`; a missing or malformed standard offset, or one followed by anything other than the end of the text, `<` or an ASCII letter: `bad std offset`; a bad daylight name: `bad dst name`; a daylight offset (present when the next character is `+`, `-` or a digit) that is malformed or followed by anything other than `,` or the end: `bad dst offset`; the text ends after the daylight part: `dst rules required`; the daylight part followed by a character other than `,`: `bad dst offset`; a malformed start date, or one followed by anything other than `/` or `,`: `bad start rule`; a malformed start time, or one followed by anything other than `,`: `bad start time`; nothing after the `,` that ends the start part, a malformed end date, or one followed by anything other than `/` or the end: `bad end rule`; a malformed end time, or one followed by anything other than the end: `bad end time`.

## Command line

32. New command: `cronq next [--zones FILE] [--zone NAME] --after INSTANT [--count N] [--horizon DAYS] EXPRESSION`, the expression one argument. `--zone` defaults to `UTC`, `--count` to 1 (1..1000), `--horizon` to 1830 (1..36600, the same check and message form as `--count`, with the word `horizon`). Without `--zones` only `UTC` exists. It prints the next `N` fire times, one per line, as local times in the agenda's form (`YYYY-MM-DDTHH:MM+HH:MM`), each found strictly after the previous. Errors follow the existing convention: exit status 2 and `cronq: <message>` on standard error (an unknown zone is `cronq: unknown zone 'X'`; a horizon miss after some lines is printed after those lines). `validate` shows a cron job's `describe()` text.
33. `cronq prev [--zones FILE] [--zone NAME | --tz RULE] --before INSTANT [--count N] [--horizon DAYS] EXPRESSION` is the mirror of `next`: each line is the fire found by `prev_before` strictly before the previous one (the first strictly before `--before`), same options, checks and output form. `cronq count [--zones FILE] [--zone NAME | --tz RULE] --from INSTANT --to INSTANT EXPRESSION` prints `count_between` as one integer line (default horizon). `--tz RULE` (also on `next`) uses the zone `parse_tz(RULE)` instead of `--zone`; giving both: `cronq: --zone and --tz are exclusive`; a bad rule: `cronq: <reason>`. All errors exit with status 2 as in rule 32.
