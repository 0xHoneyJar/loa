# Task: registration lineage — an absent predecessor is reported but not accepted, a malformed `supersedes` is an input error, and the legacy class-9 sensitivity is computed once

The cycle-132 analysis package (`evals/analysis/c132/`) reads a batch's rows against a registration file whose `supersedes` names the sha256 of the registration it replaces, forming a chain. `common.registration_chain(path)` walks it, `common.registration_provenance(path, rows)` reports it, and `common.validate_registration(path, rows)` decides which rows' `registration_sha256` are accepted (it returns the current registration's sha256). `reads.py` computes the registered sensitivities for the final read; two of them share one computation: the family `contaminated_reincluded_per_class` (one read per contamination class, under its `classes`) and the legacy single-class name `class9_nonrepo_egress_reincluded`, which is the family's `network_egress:nonrepo` member.

**Bug (observed):**
- A predecessor named by `supersedes` whose registration file is absent is still accepted: rows whose `registration_sha256` is that absent predecessor's pass validation, although nothing can be verified against its bytes.
- A `supersedes` value that is not a 64-character lower-case hex sha256 (63 characters, upper-case hex, a trailing newline, non-hex characters, free text) is accepted silently — by `validate_registration`, by `registration_provenance`, and when such a value sits in a predecessor's file on the chain.
- When only the legacy name is registered, the final read builds the whole family and then picks its `network_egress:nonrepo` member: `reincluded_family` runs although nothing registered asks for it.

**Expected:**
- A declared predecessor whose file is absent stays in the reported chain, but rows registered under it are refused: `validate_registration` raises `InputError` whose message contains `registration_sha256 differs from <current sha256, first 12 hex> on <n> row(s): <batch>/<arm>/<task>/<trial>` and names the predecessor as `<its sha256, first 12 hex> (unresolved predecessor)`. Rows under the current registration still validate and the current sha256 is returned.
- `supersedes` must be a 64-hex sha256 wherever it is read; anything else raises `InputError` containing `not a 64-hex sha256` — from `validate_registration` and `registration_provenance` alike — and `registration_chain` raises `InputError` for a malformed value inside a predecessor's file.
- With only `class9_nonrepo_egress_reincluded` registered, the final read calls `reinclude(cells, reg, seed, "network_egress:nonrepo")` exactly once and never calls `reincluded_family`; its result is byte-identical (as sorted JSON) to the family's `classes["network_egress:nonrepo"]` read when both names are registered, and the family's own read is unchanged.

Fix the bug in place and add a regression test of your own. Run the tests under `evals/analysis/c132/tests` that cover the code you change, with `python3 -m pytest -q <file>`.
